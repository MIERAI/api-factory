# 设计稿：R2 — 关联、聚合、时间运算（查询工厂的新元件）

> 版本 v0.1（2026-11-22）· 状态：**评审中**
> 上级计划：`docs/design/storefront-v2-readiness.md` 的 R2。核心代数：`docs/design/core-algebra.md`（新增元件要单独评审，本稿即评审对象）。

---

## 0. 为什么现在加、加哪些

`core-algebra.md` §9 决定 3："join 等出现 2 个以上需求再加"。现在两个使用者都有了需求：

| 形状 | storefront v2 | 试用（一家公司的参照 API） | 需求数 |
|---|---|---|---|
| **一对多嵌套**（父行 + 子行列表） | Q5 订单 + 明细 | 抬头 + 明细 1 个（新种类） | 2 |
| **按父行聚合**（子行的件数、合计） | Q6 订单历史的件数 / 金额 | — | 1（与嵌套共用基础，一起做） |
| **多对一查找**（取外键指向的那一行的列） | — | 两表关联 1、三表链式关联 1（逃生口） | 2 |
| **顶层分组聚合**（GROUP BY + 合计，可带排名） | — | 分组 + 合计 + 排名 2 个（逃生口） | 2 |
| **时间运算**（当前时间 − N、由参数推算期间） | Q7 卡住的订单 | 由参数推算上个月的期间 1 个（新种类） | 2 |

不做的（记录理由）：
- **自关联**（"本月最新"关联"上月最新"）：试用 1 个，形状特殊，继续走逃生口。
- **跨库 / 跨店铺合并 + 分组**：属于"外"（旧决定不变）。
- **多级嵌套**（孙子行）：两边都没有需求。

## 1. 共同的前提：多表

现在的流水线从一个 `scan` 开始。新元件引入**第二张以后的表**，它们一律以"从当前行出发、按键关联"的方式进入，流水线本身保持线性：

```
scan(orders) → filter → lookup(customers) → nest(order_items) → child_agg(order_items) → sort → 出口
```

- 关联的表必须和主表**在同一个数据库**（工厂的"内"：一个请求一个库）。分库表只能关联同一个分库里的表，DRC 检查分库键一致。
- 关联条件只允许**列 = 列的等值**（可以多列）。任一边为 NULL → 不匹配（和 SQL 的 `=` 一致）。
- 每张关联表在 IR 里有自己的列声明（来自 `db/schema`），参考求值器拿到的 `tables` 里有它的行。

## 2. 新元件

### 2.1 `lookup`：多对一查找

```
lookup { table, on: [(当前行的列, 对方的键列)…], columns: {新列名: 对方的列}, missing: keep | drop }
```

| 项 | 规定 |
|---|---|
| 语义 | 对每一行，在 table 里找"键列逐个等于当前行的列"的行，把指定的列加到当前行上 |
| 唯一性（DRC） | 对方的键列必须构成 table 的**主键或唯一约束** → 最多一行匹配。不是唯一键 → 编译失败（多对一以外的关联请用 nest） |
| 找不到 | `keep`（默认）：加的列全部为 NULL，类型变为可空；`drop`：丢弃这一行（内连接）。设计稿写 `找不到时: 丢弃` |
| NULL | 当前行的关联列为 NULL → 视为找不到 |
| 链式 | 后面的 lookup 可以用前面 lookup 加的列做关联（三表链式） |
| SQL | `LEFT JOIN t2 ON t1.c = t2.k`（drop: `JOIN`）。列一律带别名 |
| 参考求值器 | 对 table 的行按键建索引（键含 NULL 的行不进索引），逐行查找 |
| 覆盖条件 | 找到和找不到都出现；当前行的关联列可空时，NULL 也出现；drop 时至少一行因找不到被丢弃 |
| 变异 | keep ↔ drop；关联列换成另一列；多列键少比较一列；NULL 当作相等 |

### 2.2 `nest`：一对多嵌套

```
nest { table, on: [(当前行的列, 子表的列)…], filter?: 谓词, order: [子表的列…], max: N, as: 输出名, columns: [子表的列…] }
```

| 项 | 规定 |
|---|---|
| 语义 | 对每一行，取子表里关联列逐个相等的行，经过 filter、按 order 排序，作为一个**子行列表**加到当前行上 |
| 空 | 没有子行 → 空列表（不是 NULL，响应里是 `[]`） |
| 上限 | 子行多于 max → 整个请求 FAILED_PRECONDITION（和 `all(max)` 一样不截断：截断会静默地丢数据） |
| 顺序（DRC） | order 必须是全序：包含子表的主键或唯一键，否则编译失败（子行顺序不能依赖数据库的偶然） |
| 层数 | 只允许一层（子行里不能再 nest） |
| 和出口 | 可以和 one / all / page 组合；分页作用在父行上 |
| SQL | `LEFT JOIN LATERAL (SELECT coalesce(jsonb_agg(… ORDER BY …), '[]'), count(*) FROM (SELECT … LIMIT max+1) …) ON true`；适配器发现 count > max 时返回 FAILED_PRECONDITION |
| 类型的忠实度 | JSON 里的值按核心的 API 表示写出：十进制 → `numeric::text`（不经 JSON 数字，避免精度丢失），时间 → UTC 的 RFC3339 文本，日期 → `YYYY-MM-DD`。参考求值器按同样的表示比较 |
| 覆盖条件 | 0 个、1 个、多个子行都出现；多个子行时 order 的每一列都起作用（只反转一列的方向要能区分）；有子行被 filter 排除；有请求的子行数正好等于 max |
| 变异 | 去掉 filter；order 方向反转 / 少一列；关联列换一列；max 差一（> 和 ≥）；空列表返回 NULL |

### 2.3 `child_agg`：按父行聚合

```
child_agg { table, on: […], filter?: 谓词, aggs: { 输出名: count() | sum(列) | min(列) | max(列) } }
```

| 项 | 规定 |
|---|---|
| 语义 | 对每一行，对关联的子行（经过 filter）计算聚合值，作为标量列加到当前行上 |
| 空集合 | `count` → 0；`sum` → **0**（不是 NULL：业务上"合计 0 元"）；`min` / `max` → NULL（列可空） |
| 类型 | count → int64；sum(整数) → int64（溢出 → 查询失败）；sum(十进制) → 十进制（精确）；min / max → 原列的类型 |
| NULL | sum / min / max 忽略 NULL 的子行值（和 SQL 一致）；全部为 NULL → sum 0、min / max NULL |
| SQL | `LEFT JOIN LATERAL (SELECT count(*), coalesce(sum(x), 0), min(y) …) ON true` |
| 覆盖条件 | 0 个和多个子行都出现；sum 的列出现 NULL 值；min / max 的结果出现 NULL |
| 变异 | 空集合的 sum 返回 NULL；count(*) ↔ count(列)；去掉 filter；min ↔ max |

### 2.4 `group`：顶层分组聚合

```
group { keys: [列…], aggs: { 输出名: count() | sum(列) | min(列) | max(列) } }
```

| 项 | 规定 |
|---|---|
| 语义 | 把行集按 keys 分组，每组输出一行：keys 的值 + 聚合值（之后可以接 sort / limit / 出口） |
| NULL 键 | NULL 视为同一组（和 SQL 的 GROUP BY 一致） |
| 空集合 | 没有输入行 → 没有输出行（不输出一个合计为 0 的行） |
| 聚合 | 与 child_agg 相同的类型和 NULL 规则；空组不会出现 |
| SQL | `GROUP BY`；文本键用 `COLLATE "C"`（和参考求值器的按字节比较一致） |
| 覆盖条件 | 有多行的组和只有一行的组都出现；键里有 NULL 的组出现（键可空时） |
| 变异 | 少一个分组键；sum ↔ count；NULL 键分成多组 |

**排名**（试用里的"合计 + RANK()"）：新增 `rank { order, as }`：按 order 计算 SQL `RANK()` 语义的名次（并列同名次，下一个名次跳过）。只能放在 group 之后、出口之前。

### 2.5 时间运算（表达式元件）

| 元件 | 语义 |
|---|---|
| `now()` | 请求开始时的时刻。服务器取自时钟；**测试时可以固定**（见下） |
| `add(x, n, 单位)` | x（日期 / 时间）加 n 个单位，单位 ∈ 分钟、小时、天、月。**月的加法按 Postgres**：1 月 31 日 + 1 个月 = 2 月 28 日（或 29 日）。x 为 NULL → NULL |
| `trunc(x, 单位)` | 截到单位的开始，单位 ∈ 天、月。时间先换算到**领域的时区**再截（`AT TIME ZONE`），不受数据库会话时区影响 |

- 参数也可以是表达式的输入：`trunc(param(from), 月)` = 指定日所在月的 1 日；"上个月" = `[add(trunc(from, 月), -1, 月), add(trunc(from, 月), -1, 天)]`。
- **测试时固定 now**：服务器在 `FACTORY_TEST_CLOCK=1`（只在测试环境设置）时读请求头 `X-Factory-Now`；生产环境不认这个头。差分测试和参考求值器用同一个 now，结果可复现。
- 参考求值器的月加法、时区换算要独立实现（不调用数据库），用元件认证和 Postgres 逐值比较：每个月末、闰年 2 月、时区的日界线前后。

## 3. 设计语言（中文设计稿）的写法

```yaml
数据来源: orders

关联:                                   # 多对一(lookup)
  customer: { 表: customers, 条件: [customer_id = id], 列: { customer_name: name }, 找不到时: 保留 }

嵌套:                                   # 一对多(nest)
  items:
    表: order_items
    条件: [id = order_id]
    排序: [line_no 小到大]
    上限: 50
    列: [sku, qty, price]

子聚合:                                 # 按父行聚合(child_agg)
  item_count: { 表: order_items, 条件: [id = order_id], 计算: 件数 }
  total:      { 表: order_items, 条件: [id = order_id], 计算: 合计(price) }

筛选条件里的时间:
  stuck_before: { 类型: 时间, 来自: 现在 - 5 分钟 }      # 派生参数:不出现在请求里
```

```yaml
种类: 多条
数据来源: daily_sales
分组: { 键: [store_code], 计算: { total: 合计(amount), days: 件数 } }
排名: { 排序: [total 大到小], 输出: rank }
排序: [rank 小到大, store_code 小到大]
上限: 10
```

具体的键名在实现时以设计语言的既有风格为准（`docs/design-language.md` 由注册表生成，会同步更新）。

## 4. 差分测试：多表造数据

这是 R2 里工作量最大的部分（现在的造数据逻辑以"一张来源表"为前提）。

- **按依赖顺序造数据**：先造被引用的表（客户、订单），再造引用它的表（订单明细）。外键列的值 **约 80% 从已有的键里取**（让关联真的发生），约 20% 取不存在的值（找不到、孤立的子行），可空的外键还有 NULL。
- **子行数量要有分布**：每个父行的子行数在 0、1、多个、正好 max、max+1 之间分布，覆盖条件才能满足。
- **唯一键和平局**：沿用现有的规则（唯一列给序号、需要平局的列取密集值）。
- 覆盖条件不满足时，像现在一样换种子、数据加倍重来。

## 5. 元件认证

每个新元件在小值域上穷举，比较 Postgres 上 SQL 后端的结果和参考求值器的结果：
- lookup：键匹配 / 不匹配 / NULL，单列和两列键，keep 和 drop，两级链式；
- nest：0 / 1 / 多个 / max / max+1 个子行，filter，order 的每个方向，十进制和时间的 JSON 往返；
- child_agg / group：空集合、NULL 值、十进制求和的精度、文本键的按字节分组；
- rank：并列和跳号；
- 时间：每个月末 + 1 个月、闰年、负数、时区日界线前后的 trunc。

## 6. 实施顺序（每步一个 PR，每步都做试用验证）

| 步 | 内容 | storefront 新增 | 试用的验证对象 |
|---|---|---|---|
| **R2-1** | 多表的基础（IR 多表、DRC、多表造数据）+ `lookup` | — | 两表关联、三表链式关联 |
| **R2-2** | `nest` + `child_agg`（含适配器生成嵌套的 proto 消息） | Q5、Q6 | 抬头 + 明细 |
| **R2-3** | 时间运算（now、add、trunc、测试时钟） | Q7 | 由参数推算上个月的期间 |
| **R2-4** | `group` + `rank` | — | 分组 + 合计 + 排名 ×2 |

**试用验证的做法**（每一步结束时）：
1. 通用的改动合进 main 后，cherry-pick 到试用分支 (`trial-*`)；
2. 在试用分支上为对应的参照 API 写设计稿、生成、用差分测试验收（合成数据，不需要公司的数据库）；
3. 工作日白天（dev 数据库 7:00–21:00 运行）再做影子对比：同样的请求，比较旧服务和新服务的响应；
4. 结果（只有数字：覆盖了几个、有几处差异）记进 `storefront-v2-readiness.md` 的通用性一节。**公司的内容不进 main**（内容防护照常生效）。

R2 完成后：storefront 9 / 28；试用预计从"内 66"增加到最多 72（101 个中）。

## 7. R2.6 的追加(查询通用性的第二轮)和留下的缺口

追加(设计语言见 docs/design-language.md):

| 缺口 | 写法 | 核心 |
|---|---|---|
| 关键字的名字 | 输入 / 列叫 `limit` `from` `to` … | sqlc 参数写成 `sqlc.arg('limit')`,列名加双引号 |
| 今天 | 派生参数 / 固定条件里的 `今天` | 表达式元件 `local_date`(领域的时区的日期) |
| 子表的固定条件里的 今天 / 现在 | 嵌套 / 子聚合的 `固定条件` | nest / child_agg 的 Pred |
| 嵌套里的关联 | 嵌套的 `关联:` | 子表的来源 = scan + lookup …(`checkSource` 认 lookup) |
| 按日期的关联 | 关联的 `按日期: { 开始, 结束 / 最后一天, 参照 }`、`对方的列 = 常量` | lookup 的 `as_of` / `pred`(LATERAL … ORDER BY 开始 DESC LIMIT 1) |
| 随父的分库 | 领域的表 `分库: 随父` | 无(编译规则 + 验收的数据放置;IR 的 `shard_with_parent`) |

留下的缺口(都会在编译时报"还不支持",不会生成错的查询):

1. **由布尔输入开关的固定条件**(例: `include_closed: 布尔` 为假时加 `closed_on 为空`)。现在的写法里没有自然的位置:
   固定条件不依赖输入,筛选单元只接受和列比较的值。建议的写法: 输入的 `筛选: closed_on 为空(为假时)`
   —— 新的筛选单元 `is_null_unless(col, flag)` = `or(absent(flag), flag = true, is_null(col))`,由已有元件组合,
   不需要新的核心元件;差分测试的敏感度目标: 开关反了 / 总是筛选。没有参照的 API 需要它,这一轮不做。
2. **逻辑表(存储: JSON版本)和 R2.6 的组合**: 嵌套里的关联的子表 / 对方是逻辑表、按日期的关联 / 对方的列 = 常量的对方是逻辑表。
   做法: 子流水线 = 逻辑表的来源 + lookup;按日期的 LATERAL 里放来源的子查询(`sourceSQL`)。差分测试的造数据要把版本和日期一起造。
3. **按日期的参照是输入**(`参照: as_of` 这种请求参数): 核心的 `as_of.ref` 已经是表达式,设计语言只认列 / 今天 / 现在。
   加的时候: 编译器把输入名译成 `param`,差分测试把输入的值放在对方的开始 / 结束的前后(和派生参数的探针一样)。
4. **随父的子表的嵌套**: 编译规则和验收的数据放置(子行写进父行的库)已经有,但没有样例 API 走一遍;
   第一个用到它的 API 要同时加变异(查错库)确认差分测试抓得到。
