# 工厂就绪度：以 storefront v2 为验收标准

> 版本 v0.3（2026-11-22）· 状态：**已批准** · 进度：**R1 完成（6 / 28）**；R2-2（嵌套 / 子聚合）：Q5、Q6 → 8 / 28
> 决定（2026-11-22，用户）：**先利其器**。工厂能生成 storefront v2 所需 API 的 **95% 以上**之后，再开始开发 storefront v2。
> storefront v2 的设计书：MIERAI/storefront `docs/design/v2-microservices.md`（PR #8）

---

## 0. 为什么用 storefront v2 当验收标准

- 工厂过去的需求全部来自一家公司的参照 API（试用）：只读、单表、按店铺分库。**写操作、JOIN、聚合、消息处理**从来没有真实的需求来源。
- storefront v2 是一个完整的微服务系统，覆盖了读、写、事件、消息消费、状态机、定时任务，正好能暴露工厂的全部缺口。
- **"95%"需要一个分母**：就是下面第 2 节的 API 清单。每补一项能力，就能算出生成率提高了多少。这也是"第二个使用者"（加固计划 P7 外部验证）的第一个实例。

## 1. 遵守既有的边界决定

2026-11-17 的决定（`docs/memo/out-of-scope.md`、`boundaries.md`）继续有效：

- **查询工厂只做"内"**。扩展的方式只有"新增基本元件 + 认证"或"新的设计稿"，不能用逃生口绕过去。JOIN 和聚合按这个规矩进入查询工厂。
- **写操作不塞进查询工厂**，而是新建**命令工厂**作为另一条生产线（README 的生产线表里已经规划过）：
  - 有自己的基本元件、验证方法和边界；
  - 和查询工厂共用平台（设计语言的外壳、审查、闸门、流水线、部署）。
- **跨服务的数据不 JOIN**。"商品 + 是否有货"由 web 分别调用两个服务、在 web 里组合。这不属于工厂的范围，也不计入分母。

## 2. 分母：storefront v2 的全部 API（28 个）

|---|---|---|---|---|
| Q1 | catalog | 商品一览（按分类筛选、分页） | 单表 · 一览 | ✅ R1 |
| Q2 | catalog | 商品详情（按 SKU） | 单表 · 按键取一条 | ✅ R1 |

## 3. 要补的能力

### 3.0 平台

| 编号 | 能力 | 内容 |
|---|---|---|
| **F0** | **第二个项目** | 工厂能为**另一个仓库、另一个数据库**生成服务：独立的表结构目录、领域、proto 包名、输出目录、镜像。现在是"一个仓库、一个服务、一个库" |
| F0-R | 运行时公开 | 生成代码依赖的运行时（`platform/`）拆成可以被公开仓库引用的模块（待决定，见第 7 节） |

### 3.1 查询工厂（新增元件，需要认证）

| 编号 | 能力 | 涉及 | 要回答的问题 |
|---|---|---|---|
| **Q-J** | 一对多 JOIN、嵌套输出（父行 + 子行列表） | Q5、Q6 | 子行的上限和排序怎么规定；分页作用在父行上；参考求值器怎么实现（内存里的嵌套循环）；DRC：子表必须通过外键关联、子行必须有上限 |
| **Q-A** | 按父行聚合（计数、求和） | Q6 | 空集合的聚合结果（0 还是空）；十进制求和的精度（和现有的十进制规则一致） |
| **Q-T** | 相对时间筛选（"早于当前时间 − N"） | Q7 | "当前时间"由谁给：服务器时钟还是请求参数（差分测试要求可复现 → 由平台注入，测试时固定）；已知缺口"`A 到 B 不超过 N 天`不支持日期"一并处理 |

### 3.2 命令工厂（新的生产线）

| 编号 | 能力 | 涉及 |
|---|---|---|
| **C1** | 基本写入：插入、按键更新、按键删除；输入校验（复用 buf.validate）；乐观锁（版本号） | W1–W4 |
| **C2** | 一个请求里的多个写操作，在**一个事务**里执行（父子表一起插入、业务数据 + 审计记录） | W4、W5 |
| **C3** | 写入的标准模式：**条件更新**（满足条件才更新，影响 0 行 = 业务失败）、**幂等插入**（自然键冲突时返回第一次的结果） | M1、M10 |
| **C4** | **事件**：写操作里声明要发的事件，平台在同一个事务里写 outbox，由中继发往 RabbitMQ（发布确认）；事件契约（JSON Schema）从设计书生成 | W5、M1、M10 |
| **C5** | **消息处理器**：由 RabbitMQ 消息触发（而不是 HTTP），平台内置去重（`processed_events`）、确认、重试、死信队列 | M1–M3、M10–M12 |
| **C6** | **状态机**：声明式地写状态转移（当前状态 + 收到的消息 → 新状态 + 要发的消息）、超时转移 | W5、M4–M9、J2 |
| **C7** | **批量任务**：按条件批量写，每次有上限，定时执行 | J1 |

**命令工厂的核心思路**（README 里已经规划过）：业务逻辑写成"校验 → 业务规则 → **写操作作为数据返回**"，由平台来执行这些操作。这样一来：
- **事务、outbox、去重全部由平台统一保证**，每个生成的写 API 自动获得，不靠每个 API 自己写对；
- 业务规则仍然是纯函数（可以由 AI 写，路径闸门照样适用），可以单独测试。

## 4. 写操作怎么验证（回答备忘录留下的问题）

`out-of-scope.md` 留了问题："写的参考实现是什么？怎么在测试里验证并发和失败恢复？"这是命令工厂的设计里最重要的部分，在它自己的设计书里详细展开。这里先给出方向：

| 要验证的 | 方法 |
|---|---|
| **结果正确**（写进去的就是设计书说的） | **状态差分测试**：参考求值器在内存里维护一份"模型状态"，对同一串请求，比较"真实数据库的状态"和"模型状态"是否一致（查询工厂的差分测试比较的是返回值，命令工厂比较的是写完之后的状态 + 返回值 + 发出的事件） |
| **事务**（要么全成功，要么全不生效） | 故障注入：在第 k 个写操作之后强制失败，检查数据库回到请求之前的状态、没有发出事件 |
| **并发**（条件更新不超卖、乐观锁不丢更新） | 并发测试：N 个请求同时执行，检查不变量（库存 ≥ 0、成功次数 ≤ 初始库存、版本号严格递增） |
| **幂等**（重复的消息只生效一次） | 同一条消息投递 1 次、2 次、乱序投递，最终状态必须相同 |
| **事件不丢不多** | outbox 的事件数 = 成功的写请求数；中继崩溃后重启，事件最终全部发出（允许重复，由消费者去重） |
| **变异余量** | 沿用 `make margin`：改坏生成的代码（去掉条件、去掉去重、事务提前提交），测试必须能抓到 |

## 5. 路线和预计的生成率

按"每一期都能让 storefront v2 的一批 API 变成可以生成"来排序：

| 期 | 能力 | 新增可生成的 API | 累计 |
|---|---|---|---|
| **R1** | F0（第二个项目）+ F0-R | Q1–Q4、Q8、Q9 | 6 / 28（21%） |
| **R2** | Q-J、Q-A、Q-T | Q5、Q6、Q7 | 9 / 28（32%） |
| **R3** | 命令工厂设计书 + C1、C2、C3 + 写操作的验证体系 | W1–W4 | 13 / 28（46%） |
| **R4** | C4（事件、outbox、RabbitMQ）+ C5（消息处理器） | M1–M3、M10–M12 | 19 / 28（68%） |
| **R5** | C6（状态机，含超时） | W5、M4–M9、J2 | 27 / 28（96%） |
| **R6** | C7（批量任务） | J1 | 28 / 28（100%） |

- **过关线（95%）= R5 完成**：28 个里至少 27 个能生成，并通过工厂的验证（差分、并发、幂等、变异余量）。
- R6 是加分项。如果 C7 的投入产出比不高，J1 可以作为"手写的 5%"。

每一期都按工厂既有的流程走：设计稿 → 评审 → 实现 → 认证或验证 → 记录逃生率。

### 每期的验收方式

- 在工厂仓库里建一个 **storefront v2 的样例项目**（独立的表结构和设计书，不依赖 storefront 仓库），每一期结束时，把对应的 API 写成设计书，实际生成、编译、通过验证。
- 生成率和逃生率由 `factory stats` 统计，写进本文档第 2 节的表格。

## 6. 风险

| # | 风险 | 应对 |
|---|---|---|
| 1 | **命令工厂的验证体系**是全新的东西，工作量最大、最不确定 | R3 先写设计书并评审；状态差分测试先在 C1 上做通，再扩展到 C2、C3 |
| 2 | **状态机（C6）**可能过于复杂，做成一个"小型工作流引擎" | 只支持 saga 需要的最小集合：有限状态、消息触发、超时、每次转移最多发若干条消息。不做并行分支、子流程 |
| 3 | **范围膨胀**：为了 storefront 之外的"可能用得上"提前做功能 | 只做第 2 节清单里的形状，清单之外的需求一律记下来、不做 |
| 4 | 工厂改动影响现有的查询 API（已经在两个集群上线） | 现有的验收、差分、变异余量每期都全量跑；查询工厂的改动不能改变已有 API 的生成结果（快照比对） |
| 5 | 时间：6 期比开发 storefront 本身还长 | 这正是"先利其器"的取舍。每期结束都有可用的成果，也可以在 R5 之后就开始 storefront 的开发 |

## 7. 已决定（2026-11-22，用户）

1. **运行时公开**：拆成公开的 Go 模块（`MIERAI/api-factory-runtime`），生成代码只依赖它；工厂本身（生成器、核心代数、审查、验证）保持私有。
2. **表结构先由工厂定**：R1 的第一件事是在工厂仓库里写 storefront v2 的样例项目（表结构 + 设计书），storefront 的实现以它为准。
