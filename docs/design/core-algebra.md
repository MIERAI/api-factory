# 设计稿: 核心代数(基本元件 + 单元库)

状态: 已批准(§9 四项按推荐)· 2026-11-16

## 1. 为什么要改

现在加一个功能要改 6 个地方(中文词表 / spec / SQL 生成 / IR / 参考实现 / 测试数据合成)。
同一个语义被各层各自描述一遍,描述之间可能对不上,而且**两层错得一样时测试抓不到**:

| 实例 | 原因 |
|---|---|
| 可选的「属于」不传时返回 0 行(`cardinality(NULL)` 是 NULL) | SQL 层和参考实现对"不传"的理解不同 |
| 小数列 `> 9` 不命中 10(`numeric::text` 按字典序比较) | SQL 和参考实现**都**按字符串比较 → 自动测试全部通过 |
| 小数列 `ORDER BY` 按字典序(ORDER BY 先匹配 `::text` 的输出别名) | 同上 |
| 复合主键的合成数据冲突 / 必填条件组合后 0 行命中 | 每种模式各自手工设计数据(tieCol / keyCol / group=i/2) |
| sqlc 把视图列 `(data->>'x')::int4` 推断为 NOT NULL | 工厂没有自己的类型模型,以 sqlc 的推断为准 |
| 文本排序规则的错误在测试环境里看不出来 | 测试用的 Alpine 镜像(musl)里 `en_US.utf8` 实际按字节排,和 `C` 一样;生产不是 |

集成电路能做到超大规模,是因为: 基本元件极少且语义精确;只验证一次;复杂部件只由基本元件组合、不带新实现;
组合规则由机器检查;设计者不碰晶体管。工厂照这个结构重做。

## 2. 分层

```
中文设计稿(硬件描述语言)  ── 引用单元名 ──→  单元库(数据,不是代码)
                                                  │ 展开
                                                  ▼
                                  IR v2: 只含基本元件的流水线
                                                  │
                         ┌──────────── 设计规则检查(DRC) ────────────┐
                         ▼                                            ▼
                  SQL 后端(给服务器)                    Go 参考求值器(给测试)
                         └──────────── 差分测试: 同一数据,比较结果 ──┘
```

**只有基本元件有实现,而且只有两份(SQL / 参考求值)。** 单元库新增一条定义 = 自动获得 SQL、参考实现、测试。
**API 数增长时,核心代码量不变**,只有单元库增长。这是衡量成败的指标。

## 3. 类型(全部由核心掌握)

| 类型 | SQL | API 表示 | 比较 |
|---|---|---|---|
| int32 / int64 | int4 / int8 | 数字 | 数值 |
| text | text | 字符串 | 按字节(`COLLATE "C"`,两边一致) |
| bool | bool | bool | false < true |
| decimal | numeric | 十进制字符串 | **数值**(参考实现用精确有理数) |
| date | date | `YYYY-MM-DD` | 日期 |
| timestamp | timestamptz | RFC3339 UTC | 时刻 |

每列还有 `nullable`。类型的来源: `db/schema`(物理表)+ 单元的投影(逻辑列)。
sqlc 不再是类型的来源(见 §9 决定 1)。

## 4. 基本元件(封闭集合,目标 ≈ 20,新增要单独评审)

### 4.1 表达式(值 → 值)

| 元件 | 语义(NULL 规则写死,参考实现逐条照做) |
|---|---|
| `col(c)` / `const(v)` / `param(p)` | 列 / 常量 / 请求参数 |
| `cmp(op, a, b)` op ∈ = ≠ < ≤ > ≥ | 任一边 NULL → UNKNOWN |
| `and` / `or` / `not` | Kleene 三值逻辑 |
| `is_null(a)` | 永远 TRUE/FALSE |
| `absent(p)` | 参数未指定: 标量 = 没有 presence;列表 = 空列表或不传。**"不传"只在这里定义一次** |
| `in_list(a, p)` | a 为 NULL → UNKNOWN;列表里没有 NULL(proto 保证) |
| `starts_with(a, p)` | 按字面(% _ \ 不是通配符);a 为 NULL → UNKNOWN |
| `json_field(c, key, type)` | 键不存在或 JSON null → NULL;格式错 → 查询失败(与 SQL cast 一致) |
| `map(a, {db值 → 名字}, 默认)` | 枚举映射;未知值 → 默认(并记录指标) |
| `tuple_after(cols, dirs, params)` | 游标之后(keyset)。本可由 and/or 组合,单列为元件是为了 SQL 能用上索引(行比较) |

### 4.2 关系(行集 → 行集)

| 元件 | 语义 |
|---|---|
| `scan(table)` | 物理表 |
| `filter(pred)` | 只保留 pred 为 TRUE 的行(UNKNOWN 丢弃) |
| `project({名: 表达式})` | 计算列;输出类型由表达式推出 |
| `pick_per_key(keys, order)` | 每个键按 order 取第一行(DISTINCT ON)。keys 必须 NOT NULL |
| `sort(keys)` | 每个键带方向;**NULL 位置显式**(ASC NULLS LAST / DESC NULLS FIRST),SQL 也显式写出 |
| `limit(n)` | 前 n 行 |
| `lookup(table, on, take, missing)` | 多对一查找(R2-1,`docs/design/r2-relations.md` §2.1): 对每一行在 table 里找 on 的键列逐个相等的行,把 take 的列加上。on 的键列必须覆盖 table 的主键或唯一约束(DRC,最多一行匹配);任一边 NULL → 找不到;missing = keep(加的列 NULL,类型可空)/ drop(丢弃这一行 = 内连接);后面的 lookup 可以用前面加的列(链式)。SQL = `LEFT JOIN` / `JOIN`,参考求值器 = 按键建索引(键有 NULL 的行不进索引) |
| (以后)一对多的 `nest` / `child_agg`、顶层的 `group` | R2-2 / R2-4(`r2-relations.md`) |

### 4.3 出口(行集 → 响应)

| 元件 | 语义 |
|---|---|
| `one(not_found)` | 0 行 → NOT_FOUND;1 行 → 响应;>1 行 → 违反 DRC(键必须唯一) |
| `all(max)` | > max 行 → FAILED_PRECONDITION(不截断) |
| `page(size, max)` | keyset 分页 + next_page_token(= sort + tuple_after + limit(size+1) 的出口) |
| `compute(fn)` | AI 写的纯函数(模拟电路 IP: 不在单元库里,用计算例子单独验证) |

## 5. 单元库(数据)

```yaml
# 产品自带的标准单元库(示意)
等于:     { 参数: [列, 值], 定义: "or(absent(值), cmp(=, 列, 值))" }   # 必填时 absent 恒假,DRC 化简
属于:     { 参数: [列, 值列表], 定义: "or(absent(值列表), in_list(列, 值列表))" }
前缀匹配: { 参数: [列, 值], 定义: "or(absent(值), starts_with(列, 值))" }
有效期包含: { 参数: [开始列, 结束列, 日期], 定义: "and(cmp(≤, 开始列, 日期), or(is_null(结束列), cmp(≤, 日期, 结束列)))" }
每键取最新: { 参数: [键, 顺序], 定义: [ { pick_per_key: { keys: $键, order: $顺序 } } ] }
多条:     { 参数: [排序, 上限], 定义: [ { sort: $排序 }, { all: $上限 } ] }
```

```yaml
# 公司单元库(放在公司仓库,不进产品): 例如 JSON版本
JSON版本:
  参数: [原始表, 字段, 主键, 操作列=action_type, 删除值=1, 登记顺序=[registered_at, id], 逻辑删除?]
  定义:
    - scan: $原始表
    - project: { $字段..: "json_field(data, $键, $类型)", _action: "col($操作列)", ... }
    - pick_per_key: { keys: $主键, order: "$登记顺序 desc" }
    - filter: "and(cmp(≠, _action, $删除值), ...)"
```

- 中文设计稿里的「筛选: code 属于」「种类: 多条」「存储: JSON版本」就是在引用单元名。不认识的词 → 报错并列出单元库。
- 单元只能引用基本元件和其他单元,不能带代码。宏能力最小化: 参数替换、可选参数、对列表逐项展开(`$字段..`)。
- IR 里只有基本元件;每个元件记下来自哪个单元、设计稿哪一行(给审查和报错用)。

## 6. 设计规则检查(DRC)

展开后对 IR 做机械检查,任何一条不过 → 编译失败:

- 列存在;表达式两边类型一致(decimal 和 text 不能比较,**根除 §1 的字典序问题**)
- `pick_per_key` 的键、`page` 的排序列: NOT NULL;`page` 的排序列组合必须唯一(含主键)
- `one` 的筛选必须覆盖一个唯一键
- `all` 必须有 max;`page` 的 size/max 有界
- 每个请求参数都被使用;必填/可选与 `absent` 一致
- (性能,先做警告)筛选/排序的前导列没有索引 → 警告;以后接 EXPLAIN 闸门(§9 决定 4)

## 7. 两个后端

- **SQL 后端**: 每个元件一个确定的翻译,整条流水线生成一条 SQL(视图不再必要,`pick_per_key` 生成子查询)。
- **参考求值器**(Go,内存逐行): 每个元件一个函数,严格照 §4 的 NULL 规则;decimal 用 `big.Rat`;text 按字节。
  必须独立实现,**不复用生成的 SQL**(否则是拿 SQL 测它自己)。

**元件认证**(只做一次,CI 常驻): 每个元件在小值域上穷举(含 NULL、边界、% _、"10" vs "9"),
比较 Postgres 上 SQL 后端的结果和参考求值器的结果。认证通过后,组合不再逐个怀疑。

## 8. 差分测试(取代手工合成)

1. **数据**: 按列类型从很小的值域随机取值(整数 {1,2,3}、文本 {"a","b","a%","a_"}、小数 {"1.5","9","10"}、
   可空列含 NULL)。值域小 → 并列、命中、同一个键多个版本会自然出现。按物理表主键去重。
   JSON版本 这类单元直接生成物理表的行(登记 / 删除 / 逻辑删除),版本语义自然被测到。
2. **请求**: 参数从数据里出现过的值取 + 一个不存在的值 + 不传。
3. **比较**: 被测服务器的响应 vs 参考求值器的结果(经过同样的出口和类型表示)。
4. **覆盖条件**: 每个元件声明自己需要什么情况才算测到(filter: TRUE/FALSE/UNKNOWN 各出现;sort: 出现并列;
   pick_per_key: 某个键有 ≥2 行;all: 有 0 行和 >0 行的用例)。不满足 → 换种子重来,仍不满足 → 报告。
   种子固定,结果可复现。
5. **人写的用例保留**: 它们验证业务意图(工厂只能保证"做的和写的一致")。
6. **变异**: 现有 17 个 + 每个元件在 SQL 后端的变异(去掉 NULL 处理、方向反转、去掉转义……)必须全部被抓到。

`validation` 套件(proto 规则的边界值)与查询无关,保留不变。

## 9. 决定(2026-11-16 全部按推荐)

1. **Go 适配器不再用 sqlc 生成行类型**(推荐)。行的类型和可空性由核心决定,适配器自己生成扫描代码;
   sqlc 只留作 DRC 的独立检查(SQL 能否解析、类型是否一致,忽略它的可空性)。代价: 适配器多写约 200 行生成代码。
2. **单元库的宏能力**: 只做参数替换 / 可选参数 / 列表展开(推荐),不做条件分支和循环。不够用 → 新增基本元件(评审)。
3. **join**: 等出现 2 个以上需求再加(推荐)。→ **多对一的 `lookup` 已加**(R2-1,2026-11-22: 两个使用者各有需求;元件认证 + 差分测试的多表造数据 + 变异)。一对多 / 聚合按 `r2-relations.md` 的顺序继续。
4. **性能闸门**: 先只做"前导列无索引"警告;EXPLAIN 闸门另写设计稿。

## 11. E 步的测量(2026-11-16)

| 功能 | 新增基本元件 | core 改动 | 单元库(数据) | 其他层的接线 | 接线的原因(第一次出现的"种类") |
|---|---|---|---|---|---|
| 属于 | 0 | 0 | 1 行 | ~100 行 | 列表参数这种新输入(设计语法 / 差分生成列表 / 适配器) |
| 日期 / 十进制 | 0 | 0 | 0 | ~90 行 | 新类型在 API 里的表示(YYYY-MM-DD / 十进制字符串)与校验 |
| 多条 | **1(出口 all)** | 0 | 1 行 | ~155 行 | 新出口(handler / 差分)+ 模式的接线 |
| 有效期包含 | 0 | 0 | 1 行 | ~40 行 | 多列绑定(列1 / 列2) |
| JSON版本 | 0 | **93 行**(类型收窄 24 + IR 常量还原 69) | 9 行 | ~500 行 | 新的"来源"种类: 领域声明 / 逻辑表 catalog / 测试数据转换 / 差分生成 JSON |
| **不等于**(同种类的第二个) | 0 | 0 | **1 行** | **0** | —— |

结论(如实):
1. **语义层面成立**: 没有新增筛选/来源类的基本元件;core 的两处改动都不改语义(类型收窄、IR 序列化)。
   每个功能的 SQL、参考实现、差分测试都是自动得到的,而且抓到了试用里的真 bug(属于的 NULL 数组、小数按文本比较/排序、
   引擎的"先筛选再取最新")。变异 29/29。
2. **边际成本不是"每个功能 1 行",而是"每个种类第一次出现时一笔、之后 1 行"**: 新输入形态 / 新类型 / 新出口 / 多列 / 新来源,
   各付一次接线成本(40–500 行)。"不等于"证明了同种类的下一个确实是 1 行、其他层 0 行。
3. **"种类"本身是有限的吗**: 这是下一个要验证的问题。试用剩下的 API 如果只用到已有种类,曲线就收敛了。
