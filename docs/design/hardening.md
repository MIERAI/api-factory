## P1: 接线层模块化

现状(E 步实测): 新种类第一次出现时要改的地方

| 种类 | 要改的层 |
|---|---|
| 类型(日期 / 十进制) | 设计语言的类型表、proto 校验规则、例子的值、编译器的类型对照、适配器的转换、validation 边界值、差分的值域 / 表示、gen/db 的 Go 类型 |
| 出口(多条) | spec 的模式校验、设计语言的写法、响应的形状、IR、流水线部件、handler 模板、差分的期待值 |
| 来源(JSON版本) | 领域的写法、catalog 注入、来源部件、验收数据的转换、差分的数据生成 |

做法: 每个种类**一个文件**,实现一个接口;各层只查注册表,不再出现 `if kind == "date"`。

- `types/`: 中文名 / proto 类型和校验 / 核心类型 / Go 类型和转换 / 例子的值 / 边界值 / 差分的值域、不存在的值、表示
- `exits/`: 中文写法和参数 / 响应的形状 / 流水线部件 / handler 模板 / 差分的期待值和出口用例
- `sources/`: 领域的写法 / 逻辑表的列 / 来源部件 / 验收数据怎么写进物理表 / 差分的数据生成

验证: 重构前后生成的代码 diff 为空、验收 / 变异不变;然后加两个新种类实测
(类型 `时刻`(time of day)、出口 `前N条`(排序 + 取前 N 条,试用里 2 个 API 需要)),每个只加一个文件。

### P1 的结果(2026-11-17)

| 种类 | 以前(E 步实测) | 现在 |
|---|---|---|
| 新类型 | 日期 / 十进制: ~90 行,改 6~8 个文件 | 邮编: 1 个文件(注册表一次性加了"继承"和"格式 → 值域") |
| 新出口 | 多条: ~155 行,改 7 个文件 | 前N条: 2 个文件(定义 85 行 + Go 7 行),单元库 0 改动(复用 多条 的套装) |
| 新来源 | JSON版本: ~500 行,改 6 个文件 | 集中到 sources/json_versions.go;第三种来源还没有实测 |

重构前后: 生成物不变(只有 ::bigint → ::int8 和覆盖说明的文字),验收 / 变异 / 元件认证不变;试用分支 953 个验收全过。
顺带修正: stats 和 validation 漏了「多条」;分页出口用例的取值改为来源部分的行;注册表不依赖文件的初始化顺序。

### P2 的结果(2026-11-17)

对策都是结构性的(确定性的用例),不是调随机参数:
- **扫值请求**: 每个筛选参数单独取它的列出现过的值(最多 5 个)、同一行的全部参数、两两组合、不存在的值;
  前缀参数取陷阱前缀(% _ 在开头 / 中间 / 结尾);多版本来源加"只在旧版本里出现的值"
- **出口用例**: 单条 3 个不同的不存在的键;分页 不传 page_size / page_size = 0 / 不传翻到第 2 页;途中改条件每个参数各一次(最多 3)
- **多版本来源的数据**: 和常量比较的列(删除值 / 逻辑删除值)按 1/3 注入;自然键的值域扩大;
  覆盖条件加"多出来的旧版本 ≥3、最新是删除的键 ≥3"(参考求值器跑来源部分算出来)

| 变异 | 以前 | 现在(3 个种子里最少) |
|---|---|---|
| page_size 默认值 | 1 | 12 |
| NOT_FOUND → INTERNAL | 1 | 4 |
| % 的转义 | 1 | 4 |
| 小数按文本比较 | 1 | 3 |
| token 不绑定条件 | 1 | 3 |
| 逻辑删除 | 2 | 10 |

代价: 差分用例 451 → 约 750;验收时间 5 秒 → 6 秒(本地实测)。

**第二轮(试用分支暴露的)**: 试用的复合键 / 每组取一条 / 有效期的 API 上,margin 在某个种子下又出现 0 和 2。
单靠"多造请求"解决不了,最后的通用机制是:
- **条件的敏感度**: 每个筛选条件和条件里 and 的每一项,用参考求值器换成恒真,结果变了的请求要 ≥3。
  这一条覆盖了"不看有效期的结束日""筛选条件被忽略"以及以后的任何新单元,不需要逐个元件写规则
- **覆盖条件驱动的重生成**: 先用参考求值器预估覆盖(不要服务器),不满足就换派生种子重新生成数据(最多 5 次,可复现)
- 每组取一条的分组列值域缩小(组里要有多个候选);多列单元按行锚定边界(结束日 / 结束日 + 1);
  自然键只在组合少时扩大;删除的注入 1/6
- margin 本身: 有变异没执行(替换式没命中 / 执行器偶发出错)也算失败

结果: main(33 个变异)和试用分支(35 个)在 3 个种子下,差分最少都是 3。

### P3 的结果(2026-11-17)

`scripts/matrix.py` 生成 来源(普通的表 / JSON版本)× 分库 × 出口(单条 / 一览 / 多条 / 前N条)× (筛选单元, 类型) 30 对 × 必填 / 可选,
另加 没有输入 / 枚举 / 枚举的列表 / 复合主键 / 每组取一条 / 输入之间的规则,共 21 个 API。`scripts/matrix.sh` 在临时工作区里跑整条流水线。

| 轮 | 发现 | 种类 |
|---|---|---|
| 1 | 分页的排序列可能为空 → 编译器的内部错误(step 11 tuple_after …),设计者看不懂 | 设计语言的报错 |
| 1 | 日期的列表参数(属于)适配器不支持 | 适配器 |
| 2 | **分库 + 分页不选库**(分页的 handler 写死 h.q,一直查主库) | **适配器的 bug** |
| 2 | 参考求值器把所有分库的行合在一起选版本(版本的选择在各个库里分别进行) | 差分的模型 |
| 2 | 邮编(带格式的类型)的前缀匹配: 前缀永远通不过格式校验,条件永远不起作用 | 设计语言的语义 |
| 3–6 | 必填的等于条件 / 分库键的列太分散;自然键扩大的倍数;删除值的注入叠加;时间参数的必填判断(message 的 presence);来源没有行;出口要的数据(按截取前的行数);条件严格时数据量不够 | 差分的数据生成 |
| 第二代 | 枚举的列表参数(属于)适配器不支持 | 适配器 |

第二代只发现 1 个 → 收敛。差分的数据生成最后的形状: 扫值 + 最宽的请求 + 覆盖条件(含条件的敏感度、出口要的数据)驱动的重生成(换种子、数据加倍)。

**还没有覆盖的组合**(下一代矩阵的候选): 计算(要 AI)、自定义、逃生口 SQL、输出的类型转换(输出名和列名不同)、
很多列的表(性能)、分库键不是整数。

### P4 的结果(2026-11-17)

`make perf`(`factory perf`,慢,不在 accept 里): 专用的库 `factory_perf`(同样的 schema 和索引),
每张物理表用 `generate_series` 造 20 万行。和差分测试相反,追求真实的基数而不是陷阱值:
主键唯一 / 组合主键按混合进制拆行号 / 普通列约 1000 种值 / 文本约 5000 种 / 日期分布几年 / 枚举只取合法值 /
JSON版本每个键约 5 个版本、删除 2%、逻辑删除 1%。

每个声明式 API 跑 `EXPLAIN (ANALYZE, BUFFERS)`,参数取自真实的行(区间的下界取 40% 分位、上界取 60%,区间里约 20% 的行):
- 只有必填参数 / 全部参数 / 必填 + 每一个可选参数单独(只传一个非键条件往往是最坏的情况)
- 连接和服务器一样用匿名预编译语句(每次按实际参数做计划;`$p IS NULL OR …` 才能走索引)

| 规则 | 结果 |
|---|---|
| 执行时间 > 阈值(默认 50ms) | ✗ |
| 排序溢出到磁盘 | ✗,并给出排序键(要建的索引) |
| 有必填的筛选条件却对大表全表扫描 | ⚠,并给出列 |
| 只有必填参数时 0 行 | ⚠(样本没命中,计划不代表真实负载) |
| 超时,但原因是已知边界(见下) | ⚠ 已知边界,单独计数 |

**发现和修正**

| 发现 | 修正 |
|---|---|
| JSON版本的一览(没有必填条件): 给 20 万个版本排序去重,排序溢出到磁盘,86ms | ① `pick_per_key` 的文本键也用 `COLLATE "C"`(和最终排序一致;确定性排序规则下分组不变)② 示例 schema 加表达式索引 `((data->>'product_code') COLLATE "C", registered_at DESC, id DESC)` → 数据库边读索引边去重,读够 201 条就停: **0.5ms** |
| 同上,传了商品代码(属于): 还是先给全部的键取最新版本再筛选 | **筛选下推**(`core/pushdown.go`): 只引用分组键的条件和"每组取一条"可以交换 —— 同一组的行对它的结果相同。只在生成 SQL 时改写,参考求值器跑原样,所以差分测试同时在验证这个改写;元件认证加了专门的用例(文本键大小写 / 跨改名 / 键和非键混合) |
| 只传非键的可选条件(category 等): 仍然要扫全部版本,约 90ms | **已知边界**(见 boundaries.md §7)。半连接改写在"一个 API 一条静态 SQL"下不划算: 参数不传时子查询退化成全部的键,反而拖慢最常见的请求 |

闸门本身的检验: 在性能库里删掉 `orders_ordered_at_id_idx` → 4 个计划报"全表扫描,考虑索引 (ordered_at)";
删掉 `orders_customer_id_idx` → 不报(计划改用时间索引,确实没有退化)。

变异: 新增"下推: 丢掉了键上的条件";"先筛选再取最新"的变异跟着参数顺序更新(否则会因为类型错误被"抓到",理由不对)。

### P4.1 perf 修好 + 进 CI(2026-11-23)

R2 之后 `make perf` 坏了没人知道(不在 CI 里): 造数据只认 CHECK 的取值列表(`discount > 0` 插进 0),参数取样只认
第一张表的列(关联来的 `region_code` 不存在)。改成:

- **造数据**(factory/perf/gen.go、schema.go、checks.go、regex.go): 全部的表、全部的列(以前只有 API 读的列)。
  CHECK 认得的形: 取值列表 / 数值区间 / 文本长度 / `<> ''` / 正则(锚定的字符类 + 量词,唯一列按行号编码)/
  `isfinite` / `IS NULL OR …`,域(DOMAIN)的 CHECK 同样;**认不得的形是错误**(不再"碰巧满足")。
  FOREIGN KEY 和流水线的关联(lookup / nest / child_agg 的键,包括逻辑表的 JSON 键)= 引用: 子的值用父的生成式算
  (算父的第几行,不读父表),关联一定命中;组合键里有引用 = 每个父 4 个子。`ymd(列)` 读的整数列造合法的 YYYYMMDD。
  非键的值用 `hashint8`(乘法散列会让每隔 1000 行相同、同一个键的最新版本总是同一个日期)。
- **取样**(sample.go): 参数用到之前的流水线(关联、嵌套、逻辑表、分组都在内,去掉其他请求参数的条件)= 参数比较的那些行;
  一个请求的等值类条件取自同一行,区间条件在匹配这些值的行里取分位。必填但不是筛选的参数 = 第一个 OK 用例的值。
- **逃生口 SQL** 也跑(第一个 OK 用例的参数)。**perf 不认识的 API 种类 = ✗**,除非写进 `boundaryKinds` 并写明原因
  (写入 API 暂时在里面,原因: 写入检查在做)。
- **规则**: 排序溢出 ✗;有必填条件时对大表全表扫描且扔掉 ≥90% ✗(以前是 ⚠);全表扫描在嵌套循环里重复 ✗;
  执行时间 > 阈值 ✗。阈值 = `--max-ms`(参考机器上 50ms)× 倍率,倍率 = 这个库跑固定的 CPU 查询比参考机器慢几倍(≥1),
  所以 GitHub 的 runner 上同一个闸门;计划的形不随机器变。每个请求跑 3 次取最快。
- **已知边界**: 自动的(取最新版本之后的非键筛选;关联的对方是逻辑表但关联键不是它的键;包含的全表扫描)只豁免它们解释的那一项;
  项目的 `perf.yaml` 按 API 列出(必须写原因),不再失败时 perf 提示删除。
- **CI**: `scripts/perf.sh`(= `make perf`)每次起一个新的 Postgres 容器,本仓库 + examples/ 的每个项目依次跑(串行: 阈值按库校准,
  并行会互相干扰);verify 工作流的 `perf` job。

第一次在数据量下检查 R2〜R2.7 的 API,找到 8 处缺索引(迁移 00017),2 处工厂缺口记进 perf.yaml(筛选不下推过关联;
JSON 整数键的带校验 cast 对不上表达式索引)。

### P4.2 写入 API 的 perf(2026-11-23)

以前 perf 跳过所有没有查询流水线的 API(新建 / 按键更新 / 按键删除 / 组合命令 / 消息处理 / 状态机)。现在(factory/perf/write.go、
writecheck.go、concurrency.go)用**生成的处理器同样的代码**造出写操作: IR 的操作(command.OpsOf;状态机的转移 =
适配器的 `MachineTransitionOp`)→ 运行时的 `txn.Build` / `txn.RunIn` / `txn.Executor`。运行时自己的写(outbox、消费端去重)
不在这里: 那是 runtime/outbox 的性能闸门(runtime.yml 的 perf job),不重复。

请求的值: 更新 / 删除的键(和版本、守卫里 `列 = 输入`)取**表里现有的行**(每个请求不同的行;条件要的状态 `列 = 常量`;
同一个输入也是别的表的键时那边也存在;删除的行没有子行);新建的列取数据生成器的**新行**(第 n+1 … 行: 新的键、引用已有的父、
满足 CHECK);`列 >= 输入`、`列 = 列 - 输入` 的输入 = 1;每项 3 个元素(请求级的值和元素的键在同一个表时,取同一组的行)。

- (a) **EXPLAIN**: 一个请求的每个操作在请求的事务里 `EXPLAIN ANALYZE`(保存点回滚,整个事务最后回滚)。✗: 按键的写入却全表扫描;
  外键检查(触发器)或语句超过阈值。状态机的定时扫描(到期)/ 读实体 / 载入也 EXPLAIN(全表扫描扔掉 ≥90% = ✗)。
  静态规则: 有 API 删除父表的行 → 每个引用它的外键在子表上要有以外键列开头的索引(否则每次删除扫子表全表)。
- (b) **并发的锁**: N 路(默认 8)× 每路 100 个请求,不同的键;采样 pg_stat_activity / pg_locks(5ms)。✗: 持有行级以上的锁
  (比 ROW EXCLUSIVE 强的表锁、object 锁 —— 例如提交时 NOTIFY 的数据库锁、advisory 锁);等锁(relation extension 除外)
  的样本 > 1%(不同的键在互相等: 共用的计数行、每个请求都改的父行 …)。
- (c) **扩展性**: 同一次运行里 N 路吞吐 ÷ 1 路吞吐 ≥ 1.5(`--min-scale`;比值,不是绝对值)。
- 业务结果(找不到 / 版本冲突 / 条件不满足 / 唯一 / 外键 / CHECK)超过一半 → ✗(perf 造的请求不对,检查没有意义)。

闸门本身的检验(一次性的库): 在 jobs 上加 `pg_notify` 的触发器 → create-job ✗(object AccessExclusiveLock pg_database;
等锁 86%;1.34×);job_requests 的插入触发器更新同一个计数行 → submit-job-request ✗(transactionid / tuple 等锁 85%;1.10×);
加一个没有索引的外键子表 → delete-job ✗(外键检查要扫子表全表)。

### P5 的结果(2026-11-17,收住)

**方法**: `scripts/review-converge.sh` 对试用的 10 本中文式样书**删掉所有回答记录**,反复"审查 → 按推荐的选项回答 → 重新生成",
统计几轮通过(`factory review-stats`)。按推荐回答 = 模拟设计者。

| 实测 | 改了什么 | ≤2 轮 | 没通过 | 第 2 轮以后挡流水线的问题主要是 |
|---|---|---|---|---|
| 1 | 轮次 + 收敛规则(重复丢弃 / 严重度不升级 / 迟到) | (无效: 自动回答的脚本出错,一条都没写进去) | — | 暴露: 没回答的问题,审查员不再提就消失了 |
| 2 | 没回答的挡流水线的问题机械地继续挡 | 4/10 | 2 | 回答的行为工厂做不到(读不了的值"当作没有值")、规则文字不会被执行、同一种异常无限细分 |
| 3 | prompt: 工厂固定的数据语义 / 声明式 API 的选项只能是保持现状或改设计 | 4/10 | 0 | 回答要改输入定义(必填 / 最多 N 个 / ≥1),只写成了规则文字 |
| 4 | 设计语言: 列表的 个数 / 元素的约束;回答带 input_change 直接改设计稿(这次改了 7 处) | **7/10** | 1 | 输入之间的规则"至少指定一个"设计语言写不出来 |

每种配置只跑了一次,AI 有抽样噪声,2 → 3 的 4/10 vs 4/10 分不出差别;3 → 4 的提升和"回答落不了地"的消失对得上,比较可信。

**留下的机制**
- 轮次从审查目录推出(`factory/review`),第 2 轮以后: 和回答过的问题相同 → 丢弃;严重度不能升级;上一轮就能问的新 major → "迟到"(显示不挡);
  **上一轮挡流水线、没回答的问题,审查员不提也继续挡**,并带进这一轮(factory answer 能回答)
- 审查 prompt: 工厂固定的数据语义;声明式 API 的选项;`input_change`(必填 / 范围 / 长度 / 个数,由约束的注册表决定)
- `factory answer` 选中带 input_change 的选项 → 只改设计稿里那一行输入(保留注释,写法不对时拒绝)
- `factory answer … F1=@design[:说明]`: 已经直接改了设计书 → 只记录(下一轮算"已回答"),审查员确认改法真的解决了问题

**顺带修掉的工厂问题**(审查员的问题暴露的)
- **JSON 字段的读取: SQL 和参考求值器不一致**(`2026/01/10`、`20260110`、`1e2`、`tr` Postgres 能读,参考求值器报错)。
  差分的数据从来不生成这种写法,一直没测出来。SQL 改成先用同一个正则检查格式,元件认证加 28 个用例(旧 SQL 下 16 个失败)
- 并行审查共用 buf 的输出文件(读到写了一半的文件)

**为什么收住**: 继续调审查员的 prompt,是在拿一个噪声很大的指标拟合 10 本公司的式样书,和"工厂本身变简单、变通用"关系不大。
更有用的指标是**审查问题里有多少是设计语言的缺口** —— 它直接指出工厂下一步要加什么。这一轮暴露的缺口:

| 缺口 | 状态 |
|---|---|
| 列表的个数、元素的范围 / 长度 | ✅ 加了(约束的注册表) |
| 文本的字符种类("商品コード只能是数字") | ✅ 加了: 约束 `格式: 数字 / 英数字`(注册表的第 5 种,一个文件) |
| 输入之间的规则"至少指定一个" | 未做(输入之间的规则现在有"早于""不超过 N 天") |

### 接线层: 输入约束的注册表(2026-11-17,P5 之后回到 P1)

P1 把类型 / 出口 / 来源做成了"一个文件一种",**输入约束没有做**: 加"列表的个数"时改了 5 个地方
(IR 的字段、读 proto 的规则、设计语言的解析、编译、自动边界用例),差分的值域还是另外两张表(范围 / 格式)。

`factory/constraints`: 一种约束一个文件,同时提供 设计语言的写法和检查 / protovalidate 规则 / 边界用例 / 差分的值域(含"第 i 个合法的值")。
列表由框架处理(元素级的约束加 `repeated.items.`,边界值包成列表);IR 只保存原始规则(JSON),加约束不改 IR。

| 约束 | 设计语言 | 文件 |
|---|---|---|
| 范围 | `范围: "> 0"` / `"0~100"` | range.go |
| 长度 | `长度: 1~64` | length.go |
| 个数 | `个数: "0~1000"`(列表) | count.go |
| 枚举 / 类型的格式 | (类型自动带) | enum.go / typeformat.go |
| **格式**(新,验证用) | `格式: 数字 / 英数字` | **format.go,只有这一个文件** |

重构前后生成的 proto 和验收用例相同(920 个)。加"格式"时 margin 抓到一个回归: JSON版本的自然键有了格式约束后
只能取 5 个值,键太少,删除 / 逻辑删除的变异在某些种子下只被 0~2 个用例抓到。修正(都是通用的):
- 值域可以给出"第 i 个合法的值"(Expand),自然键需要很多不同的值时用它
- **条件的敏感度也覆盖来源里取最新之后的筛选**(删除 / 逻辑删除)。以前"最新是删除或逻辑删除的键 ≥3"是合在一起数的,逻辑删除可能根本没测到

### 接线层: 输入之间的规则的注册表(2026-11-17)

以前: 设计语言里 2 种写法("A 早于 B" / "A 到 B 不超过 N 天")用 if 链编译成 CEL,id 是 `rule_1`;
IR 里只有"有消息级规则"一个标志;**边界用例全部要人写**。试用的审查里"至少指定一个"写不出来,一个 API 审了 5 轮没通过。

`factory/constraints/rel_*.go`: 一种关系一个文件,提供 设计语言的写法 / CEL / 边界用例。
CEL 的 id 写成 `关系名.参数…`,编译器从 proto 读回 IR(`Message.Relations`),验收生成器按 id 找到关系,自动生成用例。
"没有指定时放行"的写法(可选的标量和时间 `has()`、列表 `size() > 0`)和"合法的用例不能去掉必填字段"由框架统一处理。

| 关系 | 设计语言 | 自动用例 |
|---|---|---|
| 早于 | `A 早于 B` | 相等(违反)/ 晚一点(违反)/ 早一点(合法)/ 只指定 B(合法,A 不是必填时) |
| 不超过 N 天 | `A 到 B 不超过 N 天` | 正好 N 天(合法)/ N 天 + 1 秒(违反) |
| **至少指定一个**(新) | `A、B 至少指定一个` | 都不指定(违反)/ 只指定其中一个(合法,每个) |

- 手写的 proto 里不是这种 id 的 CEL 规则: 工厂不认识,仍然标为"需要人写用例"
- 审查的选项可以带 `add_rules`(只能用注册过的写法),`factory answer` 选中后加进设计稿;
  `input_change` 能改的键、prompt 里列出的写法都从两个注册表生成(不再各处硬编码)
- 验证: 示例 ListProductMaster 加 `category、product_codes 至少指定一个` → 人写的例子里输入为空的那一条
  被正确地判为不合法(设计者加规则时例子也要改),改例子后通过;自动用例 +12

### margin 的提速(2026-11-24)

201 个变异 × 3 个种子,本地 12 核(同时有别的负载,数字是同一台机器上的对比):

| | 以前 | 现在 | 做法 |
|---|---|---|---|
| 编译 | 142–212 s | 7–10 s | 变异体合编(`factory/mutant`): 所有变异编进一个服务器,`FACTORY_MUTANT=<序号>` 选择;单元测试只跑变异所在的包,测试二进制每包编译一次 |
| 验收(3 种子) | 404–532 s | 212–261 s | 早停: 一个变异的差分用例失败够 3 个就停(`FACTORY_ACCEPT_STOP_AFTER`,`factory/accept/early.go`)|
| PR(1 种子,没有缓存 = 改了工厂核心) | — | 88–110 s | `MARGIN_SEED_COUNT=1` |
| PR(只改了一个领域) | — | 10 s | 结果缓存(`scripts/margincache.py`,内容寻址;命中 159/201) |
| PR / main(什么都没变) | — | 2 s | 缓存全部命中 |

- **测量**(早停之前,603 个(变异, 种子)): 第 3 个差分失败出现在第 22 个用例(中位数;p90 73,最大 382),
  受影响范围的用例数中位数 66(p90 276,最大 623);第 3 次之后的用例占全部的 62%。验收的时间里固定的部分
  (服务器启动、数据生成、人写 / 自动用例)占得多,所以早停只省 35%。
  编译: 每个变异 go build 平均 6.5 s + go test ./internal/... 平均 5.9 s。
- **判定不变的证明**: 同一份代码 早停 / 不早停 全量跑: 603 个(变异, 种子)的差分次数逐个等于 min(不早停, 3),
  不够 3 的集合相同(main: 都是空;故意弱化 —— 不跑出口自己的用例 —— 之后: 同样的 7 个)。
  早停的计数在每份式样书结束时核对(结果里每个失败的差分用例都计过数、个数相等),不一致 = 验收报错。
- **确定的顺序**: 消息处理器的差分以前同一个种子每次造出不同的数据(map 的遍历顺序、`ReadRows` 没有 ORDER BY),
  次数在 20–34 之间跳。修了之后同一个种子两次运行的用例和结果相同(并发用例的重试次数这种时间相关的除外)。
  顺序确定之后暴露: "如果 的边界 >= 写成 >" 在 s2 下只有 2 次(以前是运气)→ 差分加了"刚好等于常量"的消息(≥ 4 条),现在 12–22 次。
- **合编等价**: 合编和单独编译的判定逐个相同(上面的全量对比用的是合编;`SCHEMATA=0` 是单独编译)。
  合编不了的形状(改了 import、两个声明、参数没有名字 …)自动退回单独编译。
- **缓存的键**: 变异(名字 / 文件 / 替换式 / 原文件 / 变异后) + 全局(除 design/ docs/ examples/ .github/ 说明以外
  不按领域划分的全部文件: factory/ 全部、runtime/、cmd/、db/、go.mod …) + 领域(specs/、gen/acceptance、
  internal/handler、proto、gen/db 里这个领域的文件) + Go 版本 + 种子 + 早停的门槛。`NO_CACHE=1` 不读缓存。
- **CI 分层**: PR 1 个种子;合并到 main(release)和每月(`margin-monthly.yml`)3 个种子;都带缓存 + 早停。
  验收的 3 个种子从 verify 拆成 3 个并行 job(`scripts/ci/accept.sh`;margin 变快后它是 PR 的关键路径)。
  每月失败 → issue(标签 `margin-monthly`)。剩下的大头: `catalog.list-product-costs` 一个 API 占验收时间的 46%
  (参考求值器生成定向请求,单线程 60–110 s;和变异无关,同一个 (API, 种子) 的请求可以复用 —— 没做)。

### P6 的结果(2026-11-17)

按代码盘点了每一层依赖 Go / Postgres / 中文的地方(docs/memo/portability.md)。整理掉的泄漏:

| 泄漏 | 修正 |
|---|---|
| 类型的注册表里有 Go 类型(核心知道适配器的事) | 挪进 Go 适配器(`goTypes`);类型有了和自然语言无关的内部 ID |
| `main.go` 直接调用 Go 适配器 | 适配器在 init 里登记,按清单的 name 选择 |
| 新加的出口 / 类型,适配器没有实现时要等到生成代码才发现 | 完备性测试(`go test`): 注册表里的每种出口 / 类型都要有实现 |
| 后加的筛选单元(属于 / 有效期包含 / 不等于)的中文名漏进 spec 和 IR;映射表 3 份,6 处"prefix 或 前缀匹配"的双重判断 | 单元库给每个单元内部名(`{ id: in, 定义: … }`),映射只在单元库一处;spec / IR 只用内部名 |

**设计语言的边界**: `docs/design-language.md` 由 `factory doc` 从注册表生成(种类 / 来源 / 类型 / 输入和输出的键 / 约束 / 筛选单元 / 输入之间的规则),
`make check` 用 `--check` 确认是最新的。设计语言能写什么 = 这份文档;写不了的是"外"或逃生口。

所有修正前后,生成的 SQL / Go 代码不变,验收用例数相同。

顺带发现: 输入之间的规则的 CEL id 用了 `/`(`before/a/b`),buf lint 不允许(只能 a-z 0-9 . _ -);protovalidate 运行时不检查,
验收照常通过,接线层那一步没有跑 `make check` 所以没发现。改成 `before.a.b`。
