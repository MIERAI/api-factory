# 加固计划(2026-11-17)

背景: 能力评估里"做得差的"8 项。工厂只做"内"(外 → docs/memo/out-of-scope.md)。
每一项都有**衡量标准**,达到才算收敛。

| 顺序 | 项 | 收敛的标准 | 状态 |
|---|---|---|---|
| P0 | ⑥ 流程防护 | 试用公司的内容无法提交进产品分支;运行前能查出环境问题 | ✅ content-guard(pre-commit / make check / pre-push)+ make doctor |
| P1 | ① 接线层模块化 | 新"种类"第一次出现的接线: 40~500 行、分散 5 层 → **一个文件**。用两个新种类实测 | ✅ 类型(factory/kinds): 新类型「邮编」= **1 个文件 12 行**。出口(factory/exits + adapters/golang/exit_*.go): 新出口「前N条」= **2 个文件**(定义 + Go handler;语言适配器本来就按语言分开)。来源(factory/sources): 普通的表 / JSON版本 集中到各自一个文件(还没有第三种来源可以实测;配置完全不同的来源要给 spec.Storage 加字段)|
| P2 | ② 差分测试加固 | 每个变异被 **≥3** 个用例抓到;陷阱值的出现写进覆盖条件(不靠手调) | ✅ `make margin`: 3 个随机种子 × 33 个变异,差分最少 3(例外 1 个: 未知枚举值的指标,数据库的 CHECK 不允许插入,归单元测试)|
| P3 | ③ 成熟度 | 自动生成"种类组合矩阵"的 API 跑一遍,直到**不再出新的通用 bug** | ✅ 第一代 17 个 API: 6 轮修了 12 个问题;第二代 +4 个 API(枚举 / 复合主键 / 每组取一条 / 输入之间的规则): 1 个问题。3 个种子全过(`scripts/matrix.sh`)|
| P4 | ④ 性能 | 接近真实的数据量 + EXPLAIN 闸门(全表扫描 / 排序溢出 → 警告或失败) | ✅ `make perf`: 每表 20 万行,55 个计划。修了 1 个真问题(取最新版本全表排序溢出 → 排序规则统一 + 索引 + 筛选下推),1 个已知边界 |
| P5 | ⑤ 审查成本 | 审查 **≤2 轮**收敛(统计每个 API 的轮数) | ✅(收住)试用 10 本从零开始: ≤2 轮 4/10 → 7/10(各一次,有噪声)。主要收获不是审查员,而是审查暴露的设计语言缺口(列表个数、回答改不了设计、JSON 读取的语义分歧) |

| P7 | ⑧ 外部验证 | 准备好第二个人用的材料;真实数据和使用者需要协调 | |

## P1: 接线层模块化

现状(E 步实测): 新种类第一次出现时要改的地方

| 种类 | 要改的层 |
|---|---|
| 类型(日期 / 十进制) | 设计语言的类型表、proto 校验规则、例子的值、编译器的类型对照、适配器的转换、validation 边界值、差分的值域 / 表示、gen/db 的 Go 类型 |
| 出口(多条) | spec 的模式校验、设计语言的写法、响应的形状、IR、流水线部件、handler 模板、差分的期待值 |
| 来源(JSON版本) | 领域的写法、catalog 注入、来源部件、验收数据的转换、差分的数据生成 |

做法: 每个种类**一个文件**,实现一个接口;各层只查注册表,不再出现 `if kind == "date"`。

- `types/`: 中文名 / proto 类型和校验 / 核心类型 / Go 类型和转换 / 例子的值 / 边界值 / 差分的值域、不存在的值、表示
- `exits/`: 中文写法和参数 / 响应的形状 / 流水线部件 / handler 模板 / 差分的期待值和出口用例
- `sources/`: 领域的写法 / 逻辑表的列 / 来源部件 / 验收数据怎么写进物理表 / 差分的数据生成

验证: 重构前后生成的代码 diff 为空、验收 / 变异不变;然后加两个新种类实测
(类型 `时刻`(time of day)、出口 `前N条`(排序 + 取前 N 条,试用里 2 个 API 需要)),每个只加一个文件。

### P1 的结果(2026-11-17)

| 种类 | 以前(E 步实测) | 现在 |
|---|---|---|
| 新类型 | 日期 / 十进制: ~90 行,改 6~8 个文件 | 邮编: 1 个文件(注册表一次性加了"继承"和"格式 → 值域") |
| 新出口 | 多条: ~155 行,改 7 个文件 | 前N条: 2 个文件(定义 85 行 + Go 7 行),单元库 0 改动(复用 多条 的套装) |
| 新来源 | JSON版本: ~500 行,改 6 个文件 | 集中到 sources/json_versions.go;第三种来源还没有实测 |

重构前后: 生成物不变(只有 ::bigint → ::int8 和覆盖说明的文字),验收 / 变异 / 元件认证不变;试用分支 953 个验收全过。
顺带修正: stats 和 validation 漏了「多条」;分页出口用例的取值改为来源部分的行;注册表不依赖文件的初始化顺序。

### P2 的结果(2026-11-17)

对策都是结构性的(确定性的用例),不是调随机参数:
- **扫值请求**: 每个筛选参数单独取它的列出现过的值(最多 5 个)、同一行的全部参数、两两组合、不存在的值;
  前缀参数取陷阱前缀(% _ 在开头 / 中间 / 结尾);多版本来源加"只在旧版本里出现的值"
- **出口用例**: 单条 3 个不同的不存在的键;分页 不传 page_size / page_size = 0 / 不传翻到第 2 页;途中改条件每个参数各一次(最多 3)
- **多版本来源的数据**: 和常量比较的列(删除值 / 逻辑删除值)按 1/3 注入;自然键的值域扩大;
  覆盖条件加"多出来的旧版本 ≥3、最新是删除的键 ≥3"(参考求值器跑来源部分算出来)

| 变异 | 以前 | 现在(3 个种子里最少) |
|---|---|---|
| page_size 默认值 | 1 | 12 |
| NOT_FOUND → INTERNAL | 1 | 4 |
| % 的转义 | 1 | 4 |
| 小数按文本比较 | 1 | 3 |
| token 不绑定条件 | 1 | 3 |
| 逻辑删除 | 2 | 10 |

代价: 差分用例 451 → 约 750;验收时间 5 秒 → 6 秒(本地实测)。

**第二轮(试用分支暴露的)**: 试用的复合键 / 每组取一条 / 有效期的 API 上,margin 在某个种子下又出现 0 和 2。
单靠"多造请求"解决不了,最后的通用机制是:
- **条件的敏感度**: 每个筛选条件和条件里 and 的每一项,用参考求值器换成恒真,结果变了的请求要 ≥3。
  这一条覆盖了"不看有效期的结束日""筛选条件被忽略"以及以后的任何新单元,不需要逐个元件写规则
- **覆盖条件驱动的重生成**: 先用参考求值器预估覆盖(不要服务器),不满足就换派生种子重新生成数据(最多 5 次,可复现)
- 每组取一条的分组列值域缩小(组里要有多个候选);多列单元按行锚定边界(结束日 / 结束日 + 1);
  自然键只在组合少时扩大;删除的注入 1/6
- margin 本身: 有变异没执行(替换式没命中 / 执行器偶发出错)也算失败

结果: main(33 个变异)和试用分支(35 个)在 3 个种子下,差分最少都是 3。

### P3 的结果(2026-11-17)

`scripts/matrix.py` 生成 来源(普通的表 / JSON版本)× 分库 × 出口(单条 / 一览 / 多条 / 前N条)× (筛选单元, 类型) 30 对 × 必填 / 可选,
另加 没有输入 / 枚举 / 枚举的列表 / 复合主键 / 每组取一条 / 输入之间的规则,共 21 个 API。`scripts/matrix.sh` 在临时工作区里跑整条流水线。

| 轮 | 发现 | 种类 |
|---|---|---|
| 1 | 分页的排序列可能为空 → 编译器的内部错误(step 11 tuple_after …),设计者看不懂 | 设计语言的报错 |
| 1 | 日期的列表参数(属于)适配器不支持 | 适配器 |
| 2 | **分库 + 分页不选库**(分页的 handler 写死 h.q,一直查主库) | **适配器的 bug** |
| 2 | 参考求值器把所有分库的行合在一起选版本(版本的选择在各个库里分别进行) | 差分的模型 |
| 2 | 邮编(带格式的类型)的前缀匹配: 前缀永远通不过格式校验,条件永远不起作用 | 设计语言的语义 |
| 3–6 | 必填的等于条件 / 分库键的列太分散;自然键扩大的倍数;删除值的注入叠加;时间参数的必填判断(message 的 presence);来源没有行;出口要的数据(按截取前的行数);条件严格时数据量不够 | 差分的数据生成 |
| 第二代 | 枚举的列表参数(属于)适配器不支持 | 适配器 |

第二代只发现 1 个 → 收敛。差分的数据生成最后的形状: 扫值 + 最宽的请求 + 覆盖条件(含条件的敏感度、出口要的数据)驱动的重生成(换种子、数据加倍)。

**还没有覆盖的组合**(下一代矩阵的候选): 计算(要 AI)、自定义、逃生口 SQL、输出的类型转换(输出名和列名不同)、
很多列的表(性能)、分库键不是整数。

### P4 的结果(2026-11-17)

`make perf`(`factory perf`,慢,不在 accept 里): 专用的库 `factory_perf`(同样的 schema 和索引),
每张物理表用 `generate_series` 造 20 万行。和差分测试相反,追求真实的基数而不是陷阱值:
主键唯一 / 组合主键按混合进制拆行号 / 普通列约 1000 种值 / 文本约 5000 种 / 日期分布几年 / 枚举只取合法值 /
JSON版本每个键约 5 个版本、删除 2%、逻辑删除 1%。

每个声明式 API 跑 `EXPLAIN (ANALYZE, BUFFERS)`,参数取自真实的行(区间的下界取 40% 分位、上界取 60%,区间里约 20% 的行):
- 只有必填参数 / 全部参数 / 必填 + 每一个可选参数单独(只传一个非键条件往往是最坏的情况)
- 连接和服务器一样用匿名预编译语句(每次按实际参数做计划;`$p IS NULL OR …` 才能走索引)

| 规则 | 结果 |
|---|---|
| 执行时间 > 阈值(默认 50ms) | ✗ |
| 排序溢出到磁盘 | ✗,并给出排序键(要建的索引) |
| 有必填的筛选条件却对大表全表扫描 | ⚠,并给出列 |
| 只有必填参数时 0 行 | ⚠(样本没命中,计划不代表真实负载) |
| 超时,但原因是已知边界(见下) | ⚠ 已知边界,单独计数 |

**发现和修正**

| 发现 | 修正 |
|---|---|
| JSON版本的一览(没有必填条件): 给 20 万个版本排序去重,排序溢出到磁盘,86ms | ① `pick_per_key` 的文本键也用 `COLLATE "C"`(和最终排序一致;确定性排序规则下分组不变)② 示例 schema 加表达式索引 `((data->>'product_code') COLLATE "C", registered_at DESC, id DESC)` → 数据库边读索引边去重,读够 201 条就停: **0.5ms** |
| 同上,传了商品代码(属于): 还是先给全部的键取最新版本再筛选 | **筛选下推**(`core/pushdown.go`): 只引用分组键的条件和"每组取一条"可以交换 —— 同一组的行对它的结果相同。只在生成 SQL 时改写,参考求值器跑原样,所以差分测试同时在验证这个改写;元件认证加了专门的用例(文本键大小写 / 跨改名 / 键和非键混合) |
| 只传非键的可选条件(category 等): 仍然要扫全部版本,约 90ms | **已知边界**(见 boundaries.md §7)。半连接改写在"一个 API 一条静态 SQL"下不划算: 参数不传时子查询退化成全部的键,反而拖慢最常见的请求 |

闸门本身的检验: 在性能库里删掉 `orders_ordered_at_id_idx` → 4 个计划报"全表扫描,考虑索引 (ordered_at)";
删掉 `orders_customer_id_idx` → 不报(计划改用时间索引,确实没有退化)。

变异: 新增"下推: 丢掉了键上的条件";"先筛选再取最新"的变异跟着参数顺序更新(否则会因为类型错误被"抓到",理由不对)。

### P5 的结果(2026-11-17,收住)

**方法**: `scripts/review-converge.sh` 对试用的 10 本中文式样书**删掉所有回答记录**,反复"审查 → 按推荐的选项回答 → 重新生成",
统计几轮通过(`factory review-stats`)。按推荐回答 = 模拟设计者。

| 实测 | 改了什么 | ≤2 轮 | 没通过 | 第 2 轮以后挡流水线的问题主要是 |
|---|---|---|---|---|
| 1 | 轮次 + 收敛规则(重复丢弃 / 严重度不升级 / 迟到) | (无效: 自动回答的脚本出错,一条都没写进去) | — | 暴露: 没回答的问题,审查员不再提就消失了 |
| 2 | 没回答的挡流水线的问题机械地继续挡 | 4/10 | 2 | 回答的行为工厂做不到(读不了的值"当作没有值")、规则文字不会被执行、同一种异常无限细分 |
| 3 | prompt: 工厂固定的数据语义 / 声明式 API 的选项只能是保持现状或改设计 | 4/10 | 0 | 回答要改输入定义(必填 / 最多 N 个 / ≥1),只写成了规则文字 |
| 4 | 设计语言: 列表的 个数 / 元素的约束;回答带 input_change 直接改设计稿(这次改了 7 处) | **7/10** | 1 | 输入之间的规则"至少指定一个"设计语言写不出来 |

每种配置只跑了一次,AI 有抽样噪声,2 → 3 的 4/10 vs 4/10 分不出差别;3 → 4 的提升和"回答落不了地"的消失对得上,比较可信。

**留下的机制**
- 轮次从审查目录推出(`factory/review`),第 2 轮以后: 和回答过的问题相同 → 丢弃;严重度不能升级;上一轮就能问的新 major → "迟到"(显示不挡);
  **上一轮挡流水线、没回答的问题,审查员不提也继续挡**,并带进这一轮(factory answer 能回答)
- 审查 prompt: 工厂固定的数据语义;声明式 API 的选项;`input_change`(必填 / 范围 / 长度 / 个数,由约束的注册表决定)
- `factory answer` 选中带 input_change 的选项 → 只改设计稿里那一行输入(保留注释,写法不对时拒绝)

**顺带修掉的工厂问题**(审查员的问题暴露的)
- **JSON 字段的读取: SQL 和参考求值器不一致**(`2026/01/10`、`20260110`、`1e2`、`tr` Postgres 能读,参考求值器报错)。
  差分的数据从来不生成这种写法,一直没测出来。SQL 改成先用同一个正则检查格式,元件认证加 28 个用例(旧 SQL 下 16 个失败)
- 并行审查共用 buf 的输出文件(读到写了一半的文件)

**为什么收住**: 继续调审查员的 prompt,是在拿一个噪声很大的指标拟合 10 本公司的式样书,和"工厂本身变简单、变通用"关系不大。
更有用的指标是**审查问题里有多少是设计语言的缺口** —— 它直接指出工厂下一步要加什么。这一轮暴露的缺口:

| 缺口 | 状态 |
|---|---|
| 列表的个数、元素的范围 / 长度 | ✅ 加了(约束的注册表) |
| 文本的字符种类("商品コード只能是数字") | ✅ 加了: 约束 `格式: 数字 / 英数字`(注册表的第 5 种,一个文件) |
| 输入之间的规则"至少指定一个" | 未做(输入之间的规则现在有"早于""不超过 N 天") |

### 接线层: 输入约束的注册表(2026-11-17,P5 之后回到 P1)

P1 把类型 / 出口 / 来源做成了"一个文件一种",**输入约束没有做**: 加"列表的个数"时改了 5 个地方
(IR 的字段、读 proto 的规则、设计语言的解析、编译、自动边界用例),差分的值域还是另外两张表(范围 / 格式)。

`factory/constraints`: 一种约束一个文件,同时提供 设计语言的写法和检查 / protovalidate 规则 / 边界用例 / 差分的值域(含"第 i 个合法的值")。
列表由框架处理(元素级的约束加 `repeated.items.`,边界值包成列表);IR 只保存原始规则(JSON),加约束不改 IR。

| 约束 | 设计语言 | 文件 |
|---|---|---|
| 范围 | `范围: "> 0"` / `"0~100"` | range.go |
| 长度 | `长度: 1~64` | length.go |
| 个数 | `个数: "0~1000"`(列表) | count.go |
| 枚举 / 类型的格式 | (类型自动带) | enum.go / typeformat.go |
| **格式**(新,验证用) | `格式: 数字 / 英数字` | **format.go,只有这一个文件** |

重构前后生成的 proto 和验收用例相同(920 个)。加"格式"时 margin 抓到一个回归: JSON版本的自然键有了格式约束后
只能取 5 个值,键太少,删除 / 逻辑删除的变异在某些种子下只被 0~2 个用例抓到。修正(都是通用的):
- 值域可以给出"第 i 个合法的值"(Expand),自然键需要很多不同的值时用它
- **条件的敏感度也覆盖来源里取最新之后的筛选**(删除 / 逻辑删除)。以前"最新是删除或逻辑删除的键 ≥3"是合在一起数的,逻辑删除可能根本没测到
