# 设计稿：R3 — 命令工厂（写入）

> 版本 v0.2（2026-11-22）· 状态：**已批准**（⚖️ D1–D3：2026-11-22 用户决定**全部按推荐**）
> 上级计划：`docs/design/storefront-v2-readiness.md` 的 R3（C1–C3 + 写操作的验证体系）。R4（事件、消息处理器）、R5（状态机）在本稿之上扩展，本稿为它们留好位置但不实现。

---

## 0. 定位

- README 的生产线表里，命令工厂一直是"计划"：**写入 = 校验 → 业务规则 → 写入操作（操作以数据的形式返回，由平台执行）**。
- `docs/memo/out-of-scope.md` 留下的问题是做命令工厂之前必须回答的：**写的参考实现是什么？怎么在测试里验证并发和失败恢复？** 本稿的 §5 回答它。
- 和查询工厂的关系：**另一条生产线**（自己的元件、验证、边界），共用平台：设计语言的外壳、式样书闸门、审查、确定性生成、路径闸门、流水线、部署、运行时、`--project`。
- 验收标准：storefront v2 的 W1–W4（新建商品、调整价格、下架商品、调整库存 + 审计记录）。

**通用性的检查**：试用（一家公司的参照 API）全部是只读的查询，**R3 无法在试用上验证**。替代办法：本稿的形状清单（§2）尽量覆盖写接口的常见类型，并在工厂仓库自己的 design/ 里为每种形状写一个与 storefront 无关的样例（任务、标签之类的既有领域），不让命令工厂只为一个使用者成形。

---

## 1. 原则

1. **业务规则是纯函数，写操作是数据。** 生成的 handler 做：校验请求 → （可选）调用业务规则的纯函数 → 得到一串写操作 → 交给平台在**一个事务**里执行 → 把结果映射成响应和错误码。写操作的执行、事务、错误映射全部在平台和生成代码里，AI 不写任何访问数据库的代码。
2. **声明能表达的，不交给 AI。** 绝大多数写接口（插入、按键更新、条件更新）的操作可以直接在设计稿里声明；只有"从请求推算字段值"这类计算才需要业务规则函数。
3. **每个写操作的成败都有明确的语义**，映射到固定的错误码（§3），不让"更新了 0 行却返回成功"这类静默失败发生。
4. **验证以状态为准**：查询工厂比较"返回值"，命令工厂比较"写完之后的状态 + 返回值"（§5）。

## 2. 形状（本稿覆盖的写接口种类）

| 种类 | 内部名 | 做什么 | storefront | 其他样例 |
|---|---|---|---|---|
| 新建 | `insert` | 插入一行，返回插入的行（含数据库生成的列：序号、默认值） | W1 新建商品 | 新建任务 |
| 按键更新 | `update` | 按主键更新指定的列；可带**乐观锁**（请求带版本号，不一致 → 冲突） | W2 调整价格、W3 下架 | 改任务的状态 |
| 按键删除 | `delete` | 按主键删除（物理删除）；逻辑删除用"按键更新"表达 | — | 删除标签 |
| 条件更新 | `update` + `条件` | 满足条件才更新（例：库存足够才扣），不满足 → 业务失败 | （R4 的库存预留） | 余额足够才扣 |
| 幂等新建 | `insert` + `幂等键` | 自然键已存在 → 返回第一次的结果，不报错、不重复写 | （R4 的支付） | 重复提交的表单 |
| 组合命令 | `command` | 一个请求里的多个写操作（上面几种的组合），一个事务 | W4 调整库存 + 审计 | 新建任务 + 第一条日志 |

不做（本稿）：批量写（多行的 `INSERT … SELECT`、按条件批量更新 → R6）、跨库写（外）、写之后发事件（R4）、消息触发（R4）、状态机（R5）。

## 3. 写操作元件和语义

### 3.1 元件

| 元件 | 参数 | SQL | 结果 |
|---|---|---|---|
| `insert` | 表、列 → 值（值 = 请求参数 / 常量 / 业务规则的输出 / 前一个操作的返回值） | `INSERT … RETURNING …` | 插入的行 |
| `update` | 表、主键 → 值、要改的列 → 值、条件?、版本列? | `UPDATE … SET …, version = version + 1 WHERE pk = … [AND version = $v] [AND 条件] RETURNING …` | 更新后的行，或"没有更新"（原因见下） |
| `delete` | 表、主键 → 值、版本列? | `DELETE … WHERE pk = … [AND version = $v] RETURNING …` | 删除的行，或"没有删除" |
| `insert_idempotent` | 同 insert + 幂等键（自然键 / 唯一约束） | `INSERT … ON CONFLICT (键) DO NOTHING RETURNING …`，没有返回行 → 读出已有的那一行 | 新插入的行或已有的行 + 一个"是否新建"标志 |

值的表达式复用查询工厂的表达式元件（col / const / param / cmp / and / or / 时间运算 …），条件也是同一套谓词（NULL 规则不变）。

### 3.2 "没有更新"的原因要区分

`UPDATE … RETURNING` 返回 0 行时，原因可能是"行不存在"、"版本不一致"、"条件不满足"。生成的代码**在同一个事务里**再读一次这一行来区分：

| 情况 | 错误码 ⚖️ D1 | 说明 |
|---|---|---|
| 行不存在 | `NOT_FOUND` | |
| 版本不一致（乐观锁） | `ABORTED`（推荐） | gRPC / Connect 的惯例：并发冲突、调用方应重读后重试。备选 `FAILED_PRECONDITION` |
| 条件不满足 | `FAILED_PRECONDITION` + 设计稿里声明的业务原因码（例：`INSUFFICIENT_STOCK`） | 调用方不该原样重试 |

### 3.3 数据库约束的错误映射

| 数据库错误 | 错误码 |
|---|---|
| 唯一约束冲突（不是幂等键） | `ALREADY_EXISTS` |
| CHECK 约束、NOT NULL | `INVALID_ARGUMENT`（请求校验应已拦住，到这里说明设计稿漏了规则 → 同时计入异常指标） |
| 外键约束 | `FAILED_PRECONDITION` |
| 序列化失败、死锁 | `ABORTED`（平台自动重试有限次数之后） |

### 3.4 事务

- 一个请求 = 一个事务，隔离级别 **READ COMMITTED**（Postgres 默认）。条件更新和乐观锁都靠单条 `UPDATE` 的原子性，不需要更高的隔离级别 ⚖️ D2（备选：组合命令用 REPEATABLE READ）。
- 组合命令里任何一个操作失败 → 整个事务回滚，返回那个操作的错误。
- 操作的顺序就是设计稿里写的顺序；后面的操作可以引用前面操作的返回值（例：新建任务返回的 id 用在日志里）。

## 4. 设计语言（中文设计稿）

```yaml
API: UpdatePrice
种类: 按键更新
数据来源: products

输入:
  sku:     { 类型: 文本,   必填: 是, 长度: 3~32, 说明: SKU, 键: sku }
  price:   { 类型: 十进制, 必填: 是, 范围: ">= 0",  说明: 新售价, 写入: price }
  version: { 类型: 整数32, 必填: 是, 说明: 读到的版本号, 乐观锁: version }

输出:                   # 更新后的行
  price:   售价
  version: 版本号

例子:
  准备数据:
    products: [ { sku: "BEAN-001", price: 1200, version: 3, … } ]
  用例:
    - 说明: 版本一致 → 更新,版本号加 1
      输入: { sku: "BEAN-001", price: "1300", version: 3 }
      结果: { price: "1300", version: 4 }
      之后: { products: [ { sku: "BEAN-001", price: 1300, version: 4 } ] }   # 写完之后的状态(命令工厂的例子必须写)
    - 说明: 版本不一致 → 冲突,什么都不写
      输入: { sku: "BEAN-001", price: "1300", version: 2 }
      错误: ABORTED
      之后: 不变
```

```yaml
API: AdjustStock
种类: 组合命令
操作:
  - 更新: { 表: stock, 键: { sku: 输入.sku }, 设置: { available: "available + 输入.delta" },
            条件: "available + 输入.delta >= 0", 不满足: INSUFFICIENT_STOCK }
  - 新建: { 表: stock_adjustments, 值: { sku: 输入.sku, delta: 输入.delta, reason: 输入.reason } }
```

- 例子里的 **`之后:`**（写完之后的状态）是命令工厂的例子的必填项：只看返回值验证不了写操作。
- 具体的键名实现时以设计语言的既有风格为准；`docs/design-language.md` 由注册表生成。
- 实现记录（R3-2）：组合命令的 `操作` 采用 R4 稿（`r4-events-messages.md` §5.1）的写法——每个操作有名字（`- 库存: { 更新: stock, … }`），后面的操作和输出用 `操作名.列` 引用；`幂等新建` 的 `键` 写成列的列表；输出写 `来自: 操作名.列`（`操作名.新建` = 幂等新建是否真的插入了）。条件不满足的业务原因码 = FAILED_PRECONDITION，消息以 `原因码:` 开头，并带 `google.rpc.ErrorInfo`（reason = 原因码）。R4 的 `每项` / `仅当` / 可重入检查加在同一个结构上（spec 的 `Command` / `CommandOp`，运行时的 `InTx` + `RunIn` / `Savepoint`）。

## 5. 验证（回答"写的参考实现是什么"）

### 5.1 参考实现：内存里的状态机

参考求值器维护一份**模型状态**（每张表的行），对每个写操作按 §3 的语义在模型上执行（独立实现，不调用数据库）：插入、按键更新、条件、版本、幂等键、唯一约束、CHECK 约束的效果都在模型里重现。

### 5.2 状态差分测试

1. 随机初始状态（沿用查询工厂的造数据：小值域、唯一列给序号）。
2. 随机的**请求序列**（不是单个请求）：键从已有的行里取 + 不存在的键；版本号有对的也有错的；条件有满足的也有不满足的。
3. 每个请求之后比较：**响应（含错误码）** + **所有相关表的完整状态**（模型 vs 数据库）。
4. 覆盖条件：每种结果（成功、不存在、版本冲突、条件不满足、幂等命中、约束冲突）都出现；组合命令里每个操作都有成功和失败的情况。

### 5.3 事务的原子性：故障注入

测试环境里，平台在第 k 个写操作之后强制失败（请求头 `X-Factory-Fail-After: k`，只在 `FACTORY_TEST_FAULTS=1` 时生效，生产环境不认 ⚖️ D3）。检查：数据库状态 = 请求之前的状态、响应是错误。对组合命令的每个 k 都做一次。

### 5.4 并发：不变量

同一个键上 N 个请求同时执行，检查由设计稿推出的不变量：
- 条件更新：条件里的不等式永远成立（库存 ≥ 0），成功次数 ≤ 理论上限；
- 乐观锁：同一个版本号最多一个请求成功，版本号严格递增，没有丢失的更新；
- 幂等新建：只有一行，所有请求得到同一个结果。

### 5.5 幂等性（为 R4 准备）

同一个请求重放 2 次、3 次：幂等新建的结果和状态与只执行 1 次相同。

### 5.6 变异余量

沿用 `make margin`，对生成的写代码做变异：去掉条件、去掉版本检查、版本号不加 1、"没有更新"的原因判断错、幂等冲突改成报错、事务提前提交、错误码换掉——每个都必须被 ≥3 个用例抓到。
