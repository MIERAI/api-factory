# 工厂的边界

状态: 草稿 · 2026-11-16(2026-11-22: 命令工厂 R3-1 / R3-2,§2.1;系统里的分层,§8)

工厂不是万能的。边界要事先写清楚,原因有三:
1. 超出边界的需求如果硬塞进工厂,核心会一直长大(违背"基本元件封闭")
2. 设计者需要在写式样书**之前**知道"这个能不能用工厂做"
3. 工厂的保证只在边界内成立;边界外的东西不能顶着工厂的名义上线

## 1. 三个区域

| 区域 | 含义 | 谁保证正确 |
|---|---|---|
| **内** | 能完全由基本元件 + 单元库表达 | 工厂: 元件认证 + 差分测试 + DRC + 变异 |
| **边缘** | 逃生口: 手写 SQL(datasource.sql)/ AI 写的纯函数(compute) | 人写的例子 + 闸门(路径、签名、sqlc 分析);**没有差分测试** |
| **外** | 工厂不做 | 交给别的方式开发;工厂只负责说"不" |

## 2. 内: 工厂保证的范围

- **只读**的查询 API(Connect / proto),**一个请求只访问一个** PostgreSQL 数据库
- 按店铺等**分库**的表(2026-11-17 决定算内): 分库键由必填的「等于」固定,平台按 FACTORY_SHARDS 选连接(DRC 检查)
- 查询 = 基本元件的流水线: scan → (lookup …)→ (nest / child_agg …)→ filter → project → pick_per_key → sort → limit,出口 one / all(≤N)/ page
- **多表的多对一查找**(2026-11-22 R2-1 起算内): 按键取同一个库里另一张表的一行(设计稿的 `关联`),可以链式。
  对方的键必须是主键或唯一约束(DRC);找不到时 保留(列为空)/ 丢弃。分库的表只能关联同一个分库里的表(条件里两边的分库键相等)。
- **一对多: 嵌套 / 子聚合**(2026-11-22 R2-2 起算内): 每一行带上同一个库里子表的行的列表(设计稿的 `嵌套`: 子行的顺序必须是全序,
  有上限,超过上限整个请求报错、不截断;没有子行 = 空列表),或者子行的 件数 / 合计 / 最小 / 最大(`子聚合`: 没有子行 → 件数 0、合计 0、最小 / 最大 为空)。
  只有一层;子行的列不能是枚举;合计里不能写表达式(用数据库的生成列)。
  还不算内的: 多级嵌套、自关联 —— 仍走逃生口
- **关联 / 嵌套 / 子聚合的对方是逻辑表**(2026-11-22 R2.5 T1 起算内): 对方可以是 存储: JSON版本 等来源单元展开的逻辑表
  (每个自然键最新的一行,删除 / 逻辑删除去掉;唯一键 = 自然键),逻辑表 → 逻辑表的链也可以。SQL 是 LATERAL 子查询,
  关联的键下推到取最新之前(需要「键 + 登记顺序」的式索引,默认的排序规则: 例 db/migrations/00007)。
  **成本**: 关联条件里对方的列不是自然键时(子表按非键的列关联),每个父行都要给对方的全部键取最新 —— 和「JSON版本 + 非键的筛选」同一个已知边界
- 查询 = 基本元件的流水线: scan → filter → project → pick_per_key → group → rank → sort → limit,出口 one / all(≤N)/ top_n / page
- **顶层的分组聚合**(2026-11-22,R2-4 起算内): `分组` = GROUP BY + 件数 / 合计 / 最小 / 最大,`排名` = RANK()。
  以前只能走逃生口(手写 SQL)或 AI 纯函数(计算);现在有元件认证 + 差分测试 + 变异(少一个分组键、合计 ↔ 件数、NULL 的键分成多组、RANK → DENSE_RANK / ROW_NUMBER)
- **分组 / 排名之后的筛选**(2026-11-22,R2.5 T2): 输入的 `筛选` 写计算 / 排名的输出名(例 `筛选: rank 小于等于`)→ 筛选接在分组 / 排名之后
  (HAVING 一类)。`名次 ≤ N` 保留并列(结果可能多于 N 行,出口用 多条 的上限兜底)。差分测试: < ↔ <=、并列跨过 N、RANK → ROW_NUMBER
- **整数编码的日期**(2026-11-22,R2.5 T3): 领域的列写 `编码: YYYYMMDD`(整数列),输入写 `编码: YYYYMMDD`(整数的输入: 不合法的日期 → 参数错误)。
  派生参数 / 日期的输入和这种列比较时,列按日期读(不合法的值永远不命中),SQL 仍按整数比较(索引能用)。输出仍是整数
- **文本的包含(部分一致)**(2026-11-22,R2.5 T4): 筛选单元 `包含`(按字面,% _ 不是通配符)。**btree 索引用不上**(`make perf` 警告;大表要 pg_trgm 的 GIN 索引或改用前缀匹配)
- 类型: int32 / int64 / text / bool / decimal / date / timestamp(+ json 作为输入)
- 结果有上限(all 必须有 max,page 有 size 上限)—— 无上限的查询 DRC 直接拒绝
- 输入校验: proto 的 buf.validate 规则(单字段 + 输入之间的 CEL)
- 业务计算: AI 写的纯函数,输入是查询结果的行,输出是响应;不做 IO

### 2.1 内: 命令工厂(写入,2026-11-22 R3-1 起)

写操作不进查询工厂,而是**另一条生产线**(命令工厂: 自己的元件、验证、边界),共用平台(设计语言的外壳、闸门、审查、确定性生成、运行时、`--project`)。

- **一个请求 = 一个写操作 = 一个事务**(READ COMMITTED,⚖️ D2 待确认): `新建`(插入一行,返回含数据库生成的列的行)、
  `按键更新`(按主键改 `写入` / `设置` 的列)、`按键删除`(按主键物理删除)。一个请求只写**一个 PostgreSQL 数据库的一张表的一行**
- 乐观锁: 整数的版本列,`WHERE 版本 = 请求的值` + 版本 + 1;0 行 → 同一个事务里再读,不存在 → NOT_FOUND,版本不一致 → ABORTED(⚖️ D1 待确认)
- 数据库的错误有固定的错误码(唯一 → ALREADY_EXISTS;CHECK / NOT NULL → INVALID_ARGUMENT + `write_rejected_total`;外键 → FAILED_PRECONDITION;
  序列化失败 / 死锁 → 重试 3 次后 ABORTED)。不会出现"更新了 0 行却返回成功"
- handler 全部确定性生成(写操作作为数据交给 `api-factory-runtime/txn`),AI 不写。
  保证: 人写的例子(必须写 `之后` 的状态)+ 状态差分测试(模型状态 vs 数据库,每种结果 ≥4 次)+ 变异(去掉版本检查、版本不加 1、错误码换掉、返回旧的行 …)
- **组合命令**(R3-2): 一个请求里按顺序的多个写操作(新建 / 幂等新建 / 更新 / 删除),一个事务;后面的操作引用前面的返回值
  (`操作名.列`,例: 数据库生成的 id)。**条件更新**: 条件在同一条 UPDATE 的 WHERE 里(并发时也不违反),不成立 → FAILED_PRECONDITION
  + 设计稿声明的业务原因码(消息的开头 + `google.rpc.ErrorInfo`)。**幂等新建**: 键(主键 / 唯一约束)已有 → 返回已有的行,不写、不报错,`新建` = false。
  值和条件只有很小的表达式(列、输入、前面的返回值、常量、现在、加减、比较、并且)。保证另外加: 故障注入(每个 k)、并发不变量、重放、变异 12 个
- 还不是内的写入(现在走"外",按计划进来): 事件 / outbox、消息处理器、对列表逐项执行(`每项`)、可重入的检查(R4);状态机(R5);批量写(R6)。
  部分更新(不传 = 不改)、条件里的 或者 / 乘除 / 函数、跨库写也还没有

## 3. 边缘: 逃生口(允许,但要付出代价)

| 逃生口 | 什么时候用 | 仍然有的保证 | 失去的保证 |
|---|---|---|---|
| 手写 SQL | 需要 join、窗口函数(RANK 以外)、分组聚合以外的聚合(count(distinct)、平均 …;分组之后的筛选已经是内)、复杂表达式,且只出现一次 | sqlc 分析(能解析、类型)、人写例子、分页包装 | 差分测试、元件认证、DRC 的语义检查 |
| AI 纯函数 | 业务计算(汇总、判定、格式化) | 签名闸门、路径闸门、计算例子、审查 | 差分测试(只验证例子覆盖到的情况) |

**规则**: 同一种逃生在 2 个以上 API 出现 → 评审能否变成单元(只用现有元件)或新元件(要认证)。
**指标**: `factory stats` 的逃生率。一个领域的逃生率持续 > 30% → 这个领域不适合工厂,如实记录,不再硬扩。

## 4. 外: 工厂不做(现在)

| 不做的 | 为什么 | 看到这种需求时 |
|---|---|---|
| 写操作(INSERT / UPDATE / DELETE、事务)—— **查询工厂** | 查询工厂的元件和差分测试只针对读 | 交给命令工厂(§2.1)。单行的新建 / 按键更新 / 按键删除、组合命令、条件更新、幂等新建已经是内;事件 / 消息、批量写还是外(R4 以后) |
| 一个请求访问多个数据库 / 跨库合并 | 元件只有一个数据源;跨库的一致性无法在测试里复现 | 拒绝,或拆成每个库一个 API 由调用方合并 |
| 按分片(店铺等)分别查询再合并(多个店铺的列表) | 同上;合并的顺序/去重语义不在元件里。**只查一个店铺的库 = 内(分库)** | 同上 |
| 调用外部服务 / 其他 API | AI 纯函数不能做 IO | 拒绝 |
| 流式 / 异步 / 推送 | 出口只有 one / all / page | 拒绝 |
| 权限 / 行级访问控制 | 平台层(认证中间件)的事,不在每个 API 里 | 交给平台 |
| 性能保证 | 还没有 EXPLAIN 闸门(只有"没有索引"的警告) | 上线前人工确认执行计划 |
| 业务意图是否正确 | 工厂只保证"做的和写的一致" | 人: 设计稿 + 人写例子 + 审查问答 |

"现在"的意思: 这张表可以缩小,但只能通过**新增基本元件 + 认证**或**新的设计稿**,不能在单元库或逃生口里绕过去。

## 5. 边界在哪里被检查(不靠人记)

| 时机 | 检查 | 结果 |
|---|---|---|
| 写式样书之前 | **受理分类**: 需求 → 内 / 边缘 / 外(按 §2–§4) | 外 → 不进工厂 |
| 设计编译 | 不认识的词 → 报错并列出单元库 | 设计者知道"没有这个单元" |
| 编译 | DRC(类型、NULL、键唯一、有上限、截取前有排序……) | 违反 → 编译失败 |
| 编译 | 逃生口必须显式写(datasource.sql / compute),并记入逃生率 | 边缘区域可见 |
| 闸门 | AI 只能写纯函数(路径、签名、禁止 import) | AI 不能越界 |
| 统计 | 逃生率、新增元件数、每个 API 新增单元数 | 边界在变宽还是被侵蚀 |

## 6. 已知的边界案例(来自试用)

- 一家公司的参照 API(101 个): 内 66 / 边缘 7 / 外 13(全部是跨店铺合并)/ 还需要新种类 15。
  内 66 里有 23 个只查一个店铺的库 → 靠「分库」才算内
- 同一批 API 里的单表查询、追加型表的版本选择 → **内**(JSON版本 单元)
- 少数 API 的业务计算(例如"前月の単価")→ **边缘**(AI 纯函数)

受理分类的第一个实际产出: 把试用的 100 本按 §1 分类,得到"内 / 边缘 / 外"的比例。这个比例就是工厂对这家公司的价值上限。

## 7. 已知的局限(待改进)

- **分库: 不存在的分库键无法识别**(2026-11-17 试用的审查 F3)。路由规则里有 `*` 兜底时,
  "这个店铺没有库"和"这个店铺没有数据"在工厂里无法区分,现在都返回空结果。
  改进方向: 路由配置可以声明"已知的键"(没有 `*`),不匹配时返回 NOT_FOUND / INVALID_ARGUMENT,
  并作为分库出口的机制用例测试。

- **JSON版本 + 非键的筛选: 成本 = 全部版本**(2026-11-17 P4)。"取最新版本之后再筛选"是语义要求
  (先筛选会选到旧版本,公司引擎就是这个问题)。只引用分组键的条件已经下推(core/pushdown.go);
  非键的条件(例如只传 category)要先给全部的键取最新版本。20 万个版本约 90ms,`make perf` 标为"已知边界"。
  改进方向: "最新版本"物化表(外,备忘录)或者按参数的有无生成多条 SQL(参数不传时不付出半连接的代价)。

- ~~**"按键取一条、找不到时返回空"**~~ → **已支持**(2026-11-17)。`找不到时: 返回空` → 响应多一个 `found`(找到 true;
  找不到时 OK + found = false,其他字段都不设置),不再返回 NOT_FOUND。分类里约 6%(原来的 API 返回 null 的单个对象)。
- ~~**自然键里可以为空的列**~~ → **已支持**(2026-11-17)。公司的表定义 167 个里 21 个(12%)的自然键有非必填的列;
  以前取数时静默地丢掉键为空的行,原来的实现(DISTINCT ON)会返回。领域的字段写 `可以为空: 是` → 空值自己是一组,响应字段可选;
  不声明时键列不为空(和以前一样)。"表定义里非必填"不一定代表实际有空值 —— 只给确实可能为空的列声明。
- **JSON 里存的数组 / 对象的字段不支持**(2026-11-17 试用量产第 2 批,1 例: scrap_slip 的 detail_data;公司的表定义 169 个里没有数组 / 对象类型)。
  SQL 侧 `data->>'键'` 能返回 JSON 原文,但参考求值器要逐字节复现 Postgres jsonb 的文本(键的顺序、空格、数字的规范化)才能做差分测试,
  只有 1 例,不做。需要时用逃生口(自定义)。
- ~~**输出改名**~~ → **已支持**(2026-11-17)。输出写 `来自: 列名`;筛选 / 每组取一条 用列名,排序 用输出名;枚举的映射按来源的列。
  能对应到单表的 99 个查询里约 12~15% 有真正的改名(另有命名习惯的不一致: orgTypeId ↔ org_typeid)。
- ~~**JSON版本 的外壳列(registered_at 等不在 JSON 里的物理列)**~~ → **已支持**(2026-11-17)。领域的字段写 `列: registered_at`(和 `键` 二选一);
  值是被选中的最新版本那一行的物理列。可以筛选 / 排序 / 输出;不能当自然键。试用的 2 个探针 + 分类里 5 个新种类需要它
  ("最后变更时间顺"、"最新登记的一条")。外壳列是排序列时,"先筛选再取最新"和"先取最新再筛选"等价(单调),不是缺陷。
- ~~**排序的方向混在一起**~~ → **已支持**(2026-11-17,多条 / 前N条)。`[changed_at 大到小, label_code 小到大]` 每列各自的方向。
  **一览(分页)仍要求方向一致**: 游标是整组的行比较 `(a, b) < (x, y)`,混合方向要展开成 OR 链(索引用不好),目前没有需要它的例子。
  差分测试新增覆盖条件: 排序的次级列只反转这一列的方向也要被 ≥3 个请求区分 —— 要求的列 = 第一个次级列 + 方向变化的列
  (请求固定的列(必填的等于 / 分库键)是常量,跳过;前面的列已唯一时等价,不要求;10 列的键不要求每一列都区分)。
- ~~**组的列表的筛选((店铺, 商品) 的组)**~~ → **已支持**(2026-11-17)。输入写 `类型: 组列表` + `组: { 列名: { 类型, 约束… }, … }` + `筛选: 组属于`;
  有一个组逐列相等就留下(不是各列分别"属于"的交叉组合)。核心元件 in_tuples: 两值(列为空 → 不相等,和 EXISTS 一致),
  SQL = 并行数组的 `unnest … WITH ORDINALITY` 按下标对齐(sqlc 没有多参数的 unnest)。有 (列1, 列2) 的索引时是"每个组一次索引扫描"。
  分类里 6 个 + 探针 1 个。限制: 组的字段名 = 列名;字段不能是枚举 / 列表 —— 原来的 "(店铺, 商品[])" 形状写成展开后的组。
- ~~**每组取一条 + 分页(一览)**~~ → **已支持**(2026-11-17)。一览也能写 `每组取一条`: 先取每组一条,游标和排序作用在取完之后的行上。
  游标列全是分组键时(通常: 按商品分组、按商品分页),游标条件下推到取一条之前(core/pushdown.go,认证 +10 例)——
  每一页只给游标之后的键取最新,不用每页把全部的键取一遍。游标列里有非键的列时不下推(正确,但每页都要给全部的键取最新)。
- ~~**固定条件(列和列比较、和常量比较)**~~ → **已支持**(2026-11-17)。设计稿顶层 `固定条件: ["new_price <> old_price 或者 deal_id = 99999999"]`
  (factory/where: 列名 / 数字 / '文本' / '日期',= <> < <= > >=,并且 / 或者 / 不是,为空 / 不为空)。和筛选一样作用在来源的列上。
  空值: 比较的任一边为空 → 不确定 → 不留下(要留下写 "或者 列 为空")。
  差分测试: 互相比较的两列造数据时约 1/3 相等、常量会出现;覆盖条件加了「或者」的每个分支(换成恒假)和
  「不确定当成成立」(内存里判断时常见的空值处理)。
- ~~**输入之间的规则"A 到 B 不超过 N 天"只能用于时间**~~ → **已支持日期**(2026-11-22,R2-3)。日期在 API 里是 "YYYY-MM-DD" 的字符串,
  CEL 里按 UTC 0 点换成 timestamp 相减(格式不对时这条规则不报,由字段的格式规则报;protovalidate 下的单元测试覆盖跨月、闰年)。
  批量压测(docs/memo/bottlenecks.md)里"期间的长度不能限制"的缺口由此解决。
- ~~**相对时间的筛选("早于 现在 − N 分钟"、"指定日的上个月")**~~ → **已支持**(2026-11-22,R2-3,docs/design/r2-relations.md §2.5)。
  设计稿的 `派生参数`: 筛选的值由 `现在` 和输入计算(核心代数的 now / add / trunc),不出现在请求里。`现在` = 请求开始的时刻
  (运行时 `clock.Now(ctx)`;测试时 `FACTORY_TEST_CLOCK=1` + 请求头 `X-Factory-Now` 固定,例子必须写 `现在`)。
  月的加减按 Postgres(月末截到最后一天),截日 / 截月和时间的天·月加减按领域的时区(夏令时的切换也按 Postgres 的规则)。
  元件认证 477 例 × 1701 行(每个月末 + 1 个月、闰年、负数、东京 / 纽约的日界线、会话时区不是 UTC)。
  **限制**: 派生参数只能用于和来源的列比较(等于 / 不等于 / 大小),不能输出、不能当排序列;单位只有 分钟 / 小时 / 天 / 个月
  (没有周 / 年;截只有 月初 / 日初);一览(分页)用到 `现在` 时每一页是各自的请求开始时刻(翻页途中边界会移动,和翻页途中数据变化一样)。

- **整数编码的日期: 限制**(2026-11-22,R2.5 T3)。只支持 YYYYMMDD;和 `现在`(时间)比较还不行(日期的输入 / 派生参数可以);
  公元前的日期(派生参数算到公元 1 年以前)在 SQL 的改写里不保证和参考求值器一致(实际不会出现)。
- **逻辑表的关联: 限制**(2026-11-22,R2.5 T1)。对方的来源不能带请求参数(逻辑表是"表",不是查询);分库的逻辑表之间的关联按普通的表的规则。

## 8. 系统里的分层: 工厂 / 运行时 / 平台 / 手写(2026-11-22)

§1–§7 讲的是**一个 API** 在不在工厂里。用工厂做一个完整的系统(例: storefront v2 的 5 个服务)时,还有很多不是 API 的东西
(部署、跨服务的联调、监控、业务特有的逻辑)。它们放在哪一层,用同一条原则判断:

**工厂只做"能从设计书确定地推出来,而且工厂自己能证明它对"的东西。** 三个问题全部是"是"才进工厂:

1. **重复吗?** 每个服务 / 每个 API 都会出现。只出现一次的不值得进工厂
2. **能声明吗?** 能写成设计书里的数据,而不是只能写成代码
3. **能证明吗?** 工厂能用自己的手段验证(参考实现、差分测试、变异、静态检查)。验证不了的东西放进工厂,只会制造"有保证"的假象

| 层 | 负责 | 例 | 谁保证正确 |
|---|---|---|---|
| **工厂** | 从设计书生成代码 + 证明 | 查询、写入、事件、消息处理器、状态机;每个服务的打包模板;跨项目的静态检查 | 认证 + 差分测试 + 变异 + DRC |
| **运行时**(公开模块 api-factory-runtime) | 每个服务都一样、写一次的库 | 事务、outbox、消费者、重试 / 死信、时钟;**埋点**(RPC / DB / 消息的 trace 透传) | 运行时自己的测试(集成测试对真的 Postgres / RabbitMQ) |
| **平台**(gitops、slo-platform、集群) | 部署和跨服务的事 | k8s 清单(共用的基础模板,每个服务只填名字和镜像)、RabbitMQ、监控、SLO、告警、压测 | 平台的演练 / 门槛 |
| **手写**(使用工厂的系统的仓库) | 只属于这个业务的东西 | 业务特有的逻辑(例: 模拟支付)、前端、**多个服务连起来的端到端测试** | 人写的测试 |

### 8.1 归属(决定)

| 需要的东西 | 层 | 理由 |
|---|---|---|
| Dockerfile、健康检查、指标端口 | 工厂(项目模板) | 每个服务都一样,能从项目确定地推出来。已做: `factory/proj/packaging.go` 从 go.mod 生成 `Dockerfile` / `.dockerignore`(init 写、`--project` 的 prepare 重写);探针 `/livez` `/readyz` `/healthz` 和 `METRICS_PORT` 由运行时提供,镜像定为 `PORT=8080` `METRICS_PORT=9090`;R4.1: `HEALTHCHECK CMD ["/server", "probe"]`(运行时的子命令请求自己的 `/readyz`;docker / compose 用,k8s 直接探 `/readyz`) |
| "准备好了"(拓扑声明好、消费循环订阅了才接流量) | 运行时(信号)+ 工厂(wiring 登记) | R4.1: `server.Workers.Ready` 的信号,全部满足之前 `/readyz` 503;只管启动(之后 RabbitMQ 断开不进 readiness,依赖的故障不摘流量) |
| 服务读哪些环境变量 | 运行时(清单)+ 工厂(写进项目 README) | R4.1: `server.Env` 是唯一的来源(运行时的测试检查它和源码一致),`factory --project . prepare` 按项目生成 README 的环境变量表,不手抄 |
| 系统级的消息拓扑(全部队列 / 绑定 / DLQ) | 工厂(生成清单)+ 平台(部署前声明) | R4.1: `factory system <目录>` 在跨项目检查之后生成 `<契约目录>/topology.json`;平台在部署服务之前执行 `factory-runtime topology apply`(k8s 的 Job / compose 的一次性容器)。服务启动时照样声明自己的队列(幂等),清单是"提前声明" |
| 路由不到的消息 | 运行时 | R4.1 决定: 命令和事件都开 `mandatory`。退回的命令留在 outbox 重试(配置错误,不能丢);退回的事件标成已发送(不堵 outbox: `外部: 是` 的事件可能永远没有队列),但留下 `last_error`、计 `factory_outbox_unroutable_total{kind,type}`、ERROR 日志 —— 清单声明之后生产环境里不该出现,出现 = 告警 |
| k8s 清单 | 平台 | 部署方式是平台的选择;工厂只产出镜像能用的东西 |
| 跨服务的消息契约对得上(每条被消费的消息有发送方、字段兼容) | 工厂(跨项目的静态检查) | 工厂看得到所有项目的设计书,能检查;不需要真的跑起来。R4.1 已做: `factory system`(`factory/system`):被消费的有发送方、发出的有接收方(或 `外部: 是`)、命令恰好一个接收方、拥有者、版本、每个项目生成时的字段 = 契约目录里现在的 |
| 多个服务真的连起来跑(saga 走完一圈) | 手写(端到端测试)+ 平台(环境) | 系统测试;工厂证明的是每个服务和契约,不是整个系统 |
| 业务特有的逻辑 | 手写,**接口由工厂生成** | 工厂生成带类型的钩子,人只写函数体;外面的事务 / outbox / 错误码仍由工厂保证 |
| 链路追踪 | 运行时 | 埋点写一次,所有生成的服务自动带上 |
| SLO | 平台;工厂只导出 API 清单(gen/api-catalog.json) | slo-platform 读清单生成默认 SLO;工厂不碰 SLO 本身 |
| 前端 | 手写 | 不重复,也不是 API |

### 8.2 "95%" 怎么量

就绪度(storefront-v2-readiness.md)数的是 **API 的个数**。它不等于工作量: 一个系统里还有手写的钩子、端到端测试、平台的配置。
所以另外要量 **手写占比**: 一个使用工厂的项目里,人写的代码(钩子的函数体、逃生口)占全部代码的比例,`factory stats` 按项目报告
(`factory --project DIR stats`;实现 `factory/proj/lines.go`)。API 个数和手写占比一起看,才能说"工厂做了多少"。

**量的范围** = 服务代码(镜像里编译的东西,和生成的 Dockerfile 复制的范围相同):

- `cmd/`、`internal/`、`gen/` 下的 `*.go`,不含 `*_test.go`(测试不进镜像;手写的端到端测试属于"手写"层,另算)
- `db/queries/*.sql`
- 不量: `design/`(设计书是输入)、`specs/` `proto/`(从设计书生成的中间产物)、`db/schema/`(设计的一部分)、Dockerfile 等配置

**生成 / 手写的界线**(按文件):

- **生成** = 文件开头的注释块(第一个代码行之前)里有 Go 的标准标记 `Code generated … DO NOT EDIT.`(`//` `--` `#` 注释都认)。
  标记写在 package 之后不算
- **手写** = 其余所有文件: compute 的逻辑(`*_logic.go`)、custom 处理器、`cmd/server/main.go` 这类项目自己的文件(init 写一次,
  之后归项目,所以算手写)
- **例外**: `db/queries/` 里从 `datasource.sql`(逃生口)抄出来的查询带生成标记,但内容是人写的 → 手写(标记里
  `from specs/…/spec.yaml` 指向的式样书写了 `datasource.sql`)
- 行 = 非空行(注释算)

报告两个比例: **手写 / (手写 + 生成)**;和更保守的 **生成只算工厂自己的输出**(标记里有 `by protoc-gen-…` / `by sqlc` 的
部分不算进分母 —— 工厂给 protoc 的输出再加一行自己的标记,所以看注释块里的全部标记)。

|---|---|---|---|---|
