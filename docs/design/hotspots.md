# 负载与热点(perf 计划的第 ③ 层)

状态: 实现中 · 2026-11-24

## 1. 原则

**设计书只问业务事实,用业务的话问;工程数字由工厂推出,或者从生产学到。**

写设计书的人(常常是新人)事先不知道 QPS、p99、键的分布。工厂存在的意义是降低难度,不是把难度搬到设计阶段。
所以:

- 工程数字(QPS、p99、键分布)**永远不是必填**。QPS / p99 = 平台按 API 种类的默认值(和 slo-platform 的默认 SLO 一致);
  键分布在正常的路径上不手写。
- 工厂自己判断该问谁。只有"共享数量的读改写"(库存扣减、计数器、余额、数值列上的条件更新)才问**一个业务问题**:
  「会不会被很多人同时抢(限时抢购等)?」 回答 `是` / `否` / `不确定`。其他 API 什么都不用答。
- 不回答不挡闸门(按 `不确定`)。AI 审查用平常的话把这个问题提出来,附上建议的回答和理由: 新人在审查里学到。
- 高级工程师的经验写进工厂一次,新人直接用上: 什么样的写会变成热点、热点了怎么办(分桶)、不确定时看什么指标,
  都是工厂的知识,不是每个设计书作者的知识。
- 专家可以在可选的 `负载:` 里写 QPS / p99 / 键分布;loadgen 和 api-perf 有就用。大多数设计书永远不写。

## 2. 工厂的自动分类

| 类 | 怎么判断(静态,从命令的操作) | 问什么 | 默认 |
|---|---|---|---|
| 共享数量的读改写 | 按键更新的操作里有 `列: "列 ± 表达式"`(数值列) | 「会不会被很多人同时抢?」`同时抢: 是 / 否 / 不确定` | 不确定 |
| 其他(查询、新建、按键更新 / 删除的普通字段) | — | 不问 | 均匀分布,现有的 EXPLAIN / 锁 / 扩展检查 |

回答的效果:

| 回答 | 生产线 | 测试 | 运行 |
|---|---|---|---|
| `是` | 分桶(§4);形状不支持分桶 → **静态拒绝**,消息说明为什么、怎么改 | 分桶的差分 + 并发不超卖 | 普通指标 |
| `否` | 普通(一行) | 现有 | 普通指标 |
| `不确定` / 没写 | 普通(一行) | 现有 | **热键监控**(§5): 写入集中度 + 等锁时间的指标和告警,真实数据显示偏斜时给出可执行的建议 |

## 3. 默认的负载(平台的默认,不写)

| API 种类 | QPS(perf 的并发检查 / loadgen 的默认速率) | p99 | 键分布 |
|---|---|---|---|
| 查询(单条 / 多条 / 一览) | 50 | 300ms(slo-platform 的 latency 默认) | uniform |
| 写入(新建 / 按键更新 / 删除 / 组合命令) | 20 | 500ms | uniform |
| 共享数量的读改写 + `同时抢: 是` | 200 | 500ms | hot:1(全部打到一个键) |

高级(可选,写了就用):

```yaml
负载:            # 专家用;大多数设计书不写
  QPS: 300
  p99: 200ms
  键分布: hot:3    # uniform | zipf:1.2 | hot:N
```

## 4. 分桶的生产线(`同时抢: 是`)

热点 = 很多请求同时改同一行: 行锁让它们排队,吞吐上限 ≈ 1 / 一次事务的时间(perf 的单键探针实测给出)。分桶 = 把一行的
数量拆成 N 行(桶),每个请求只锁一个桶。

### 4.1 适用的形状(其他形状 → 静态拒绝 + 说明)

- 表 T 有主键;数量列 Q 是整数,表上有 `CHECK (Q >= 0)`(不超卖的不变量由数据库保证)
- 写 Q 的操作: 按主键更新,`Q: "Q - x"`(取)或 `Q: "Q + x"`(还);取的操作 `条件: "Q >= x"`。同一个操作里其他的
  `设置` 只能是 `现在`(每个桶各记一份,读的时候取最大)
- 读 Q 的 API: 都经过视图(工厂改写,设计书不用管)

### 4.2 生成的东西(`db/schema/zz_factory_buckets.sql`,和当前状态表一样走迁移)

- 桶表 `factory_bucket_<T>`(T 的主键 + `bucket` + Q + 按桶记的列),`CHECK (Q >= 0)`,外键 → T(ON DELETE CASCADE)
- 视图 `factory_hot_<T>` = T 的行,Q = 桶的合计,按桶记的列 = 桶里最大的;`INSTEAD OF INSERT / UPDATE / DELETE`:
  - UPDATE: 差 d = 新 Q − 旧 Q。d < 0(取 −d): 随机选一个桶,条件更新 `Q >= −d`(热路径: 只锁这一个桶);不够 →
    按桶的顺序锁住这个键的全部桶,合计 ≥ −d 才从各桶扣,否则不更新(运行时照常判定"条件不成立",和一行的时候一样);
    d > 0: 加到随机的一个桶。其他列有变化时才写 T 的行(冷路径)
  - INSERT: 写 T(T 上的触发器把 Q 平分到 N 个桶);DELETE: 删 T 的行(桶跟着删)
- T 上的触发器: 写进 T 的 Q(新建 / 运维登记 / 数据修复 / 旧系统)= **合计设成这个值**(平分到桶),T 的 Q 保持 0;
  TRUNCATE T → 桶也清空
- 编译器: 先按 T 做全部的检查(主键、CHECK、外键),最后把 IR 里写 T 的操作和读 T 的扫描的表名换成视图;生成的 handler
  和运行时不变。验收读状态时读视图(`Table.ReadFrom`)
### 4.3 证明

- 参考实现 = 一行的模型(命令工厂的状态差分不变): 视图上看到的 Q = 模型的 Q
- 差分 + 变异(margin,表结构变异): 取的时候不检查合计 / 回退时不锁 / 加到了全部的桶 / 视图不合计 …
- 验收里的并发: 同一个键 N 个请求同时取,总数 = 成功的次数 × x,Q 不会小于 0(不超卖),成功的次数 = 能成功的最大次数
  (不会因为分桶"假的不够")

## 5. 热键监控(`不确定`)

- 运行时的指标(生成的 handler 每次写入时记录键;只给 `不确定` 的 API):
  - `factory_write_key_top_share{api}`: 最近的写入里最热的键占的比例(滑动窗口,Space-Saving top-k;键本身不进标签)
  - `factory_write_key_top_n{api,k}`: 前 k 个键(k = 1, 3)合计占的比例
  - `factory_write_lock_wait_seconds{api}`: 这个 API 的写操作的耗时直方图(等行锁的时间在里面)
- 告警规则(`gen/observability/hotkeys.rules.yaml`,Prometheus 的规则;平台的 Prometheus 照常抓 /metrics):
  前 3 个键占 80% 以上且持续 10 分钟 → ticket,消息里是建议: 「ConsumeJobQuota: 3 个键 = 80% 的写入 → 改成分桶:
  在设计书里把 `同时抢: 不确定` 改成 `同时抢: 是`」
- 以后(没有做): `factory observe` 从生产的指标读出分布,自动写回 `负载:` / 建议的回答(§7)

## 6. perf 和 loadgen

- 单键探针(信息,不失败): 按键更新的 API,8 路都打同一个键,报告"同一键约 N/s"。`同时抢: 是` 的 API 看到的是分桶之后的数字
- api-perf 的并发检查: 有 `负载.键分布` 用它,没有用默认(上表);共享数量的读改写 + `同时抢: 是` 默认 hot:1
- loadgen: `--skew` 的默认 = 声明的分布(`负载.键分布`,或者上表的默认);命令行写了就用命令行

## 7. 决定

| # | 问题 | 决定 | 理由 |
|---|---|---|---|
| H1 | 问什么 | 只问共享数量的读改写一个业务问题 | ③ 正是限时抢购的情况;让 ① / ② 也声明只会产生没有意义的 "uniform" 样板 |
| H2 | 不回答 | 按 `不确定`,闸门不失败;AI 审查提出问题 + 建议 | 不能让工厂的门槛变成新人的门槛 |
| H3 | 热点 + 不能分桶的形状 | 静态拒绝,消息里写为什么、怎么改 | 运行时才发现的热点是最贵的 |
| H4 | 分桶放在哪一层 | 数据库(视图 + INSTEAD OF 触发器 + 桶表),编译器把 IR 里的表名换成视图;T 本身不改名 | 生成的 handler / 运行时不变(和并行开发的追踪不冲突);db/schema 里人写的表不动 |
| H9 | 直接写 T 的 Q | = 把合计设成这个值(绝对值) | T 的 Q 一直是 0,`Q + 5` 这种相对的写法在 T 上没有意义;增减走 API(视图) |
| H5 | 桶数 | 8(高级: `负载.桶数`) | 8 路并发的检查下锁不排队;合计的读取 8 行很便宜 |
| H6 | 单键探针 | 只报告,不失败 | 单键的上限是物理的(行锁),只能告诉人,不能"修好" |
| H7 | 默认的 QPS / p99 | 按 API 种类的平台默认 | 和 slo-platform 的默认 SLO 一致;专家可以改 |
| H8 | factory observe(生产数据 → 建议) | 设计,不在这个 PR | 需要生产的 Prometheus 的接口约定;先有指标和告警 |
