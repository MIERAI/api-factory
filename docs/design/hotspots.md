# 负载与热点(perf 计划的第 ③ 层)

状态: 实现中 · 2026-11-24

## 1. 原则

**设计书只问业务事实,用业务的话问;工程数字由工厂推出,或者从生产学到。**

写设计书的人(常常是新人)事先不知道 QPS、p99、键的分布。工厂存在的意义是降低难度,不是把难度搬到设计阶段。
所以:

- 工程数字(QPS、p99、键分布)**永远不是必填**。QPS / p99 = 平台按 API 种类的默认值(和 slo-platform 的默认 SLO 一致);
  键分布在正常的路径上不手写。
- 工厂自己判断该问谁。只有"共享数量的读改写"(库存扣减、计数器、余额、数值列上的条件更新)才问**一个业务问题**:
  「会不会被很多人同时抢(限时抢购等)?」 回答 `是` / `否` / `不确定`。其他 API 什么都不用答。
- 不回答不挡闸门(按 `不确定`)。AI 审查用平常的话把这个问题提出来,附上建议的回答和理由: 新人在审查里学到。
- 高级工程师的经验写进工厂一次,新人直接用上: 什么样的写会变成热点、热点了怎么办(分桶)、不确定时看什么指标,
  都是工厂的知识,不是每个设计书作者的知识。
- 专家可以在可选的 `负载:` 里写 QPS / p99 / 键分布;loadgen 和 api-perf 有就用。大多数设计书永远不写。

## 2. 工厂的自动分类

| 类 | 怎么判断(静态,从命令的操作) | 问什么 | 默认 |
|---|---|---|---|
| 共享数量的读改写 | 按键更新的操作里有 `列: "列 ± 表达式"`(数值列) | 「会不会被很多人同时抢?」`同时抢: 是 / 否 / 不确定` | 不确定 |
| 其他(查询、新建、按键更新 / 删除的普通字段) | — | 不问 | 均匀分布,现有的 EXPLAIN / 锁 / 扩展检查 |

回答的效果:

| 回答 | 生产线 | 测试 | 运行 |
|---|---|---|---|
| `是` | 分桶(§4);形状不支持分桶 → **静态拒绝**,消息说明为什么、怎么改 | 分桶的差分 + 并发不超卖 | 普通指标 |
| `否` | 普通(一行) | 现有 | 普通指标 |
| `不确定` / 没写 | 普通(一行) | 现有 | **热键监控**(§5): 写入集中度 + 等锁时间的指标和告警,真实数据显示偏斜时给出可执行的建议 |

## 3. 默认的负载(平台的默认,不写)

| API 种类 | QPS(perf 的并发检查 / loadgen 的默认速率) | p99 | 键分布 |
|---|---|---|---|
| 查询(单条 / 多条 / 一览) | 50 | 300ms(slo-platform 的 latency 默认) | uniform |
| 写入(新建 / 按键更新 / 删除 / 组合命令) | 20 | 500ms | uniform |
| 共享数量的读改写 + `同时抢: 是` | 200 | 500ms | hot:1(全部打到一个键) |

高级(可选,写了就用):

```yaml
负载:            # 专家用;大多数设计书不写
  QPS: 300
  p99: 200ms
  键分布: hot:3    # uniform | zipf:1.2 | hot:N
```

## 4. 分桶的生产线(`同时抢: 是`)

热点 = 很多请求同时改同一行: 行锁让它们排队,吞吐上限 ≈ 1 / 一次事务的时间(perf 的单键探针实测给出)。分桶 = 把一行的
数量拆成 N 行(桶),每个请求只锁一个桶。

### 4.1 适用的形状(其他形状 → 静态拒绝,消息里写为什么、怎么改)

- 表 T 有主键;数量列 Q 是整数
- 写 Q 的更新: 按主键,`Q: "Q - x"`(取)或 `Q: "Q + x"`(还);取的时候 `条件: "Q >= x"`(和扣的量相同: 不超卖的规则);
  同一个操作里其他的 `设置` 只能是 `现在`(每个桶各记一份,读的时候取最大)。没有乐观锁(版本列每次都变 = 每个请求都改同一行)
- 新建: 写表本身(数量平分到桶);新建之后不能返回 Q;不能是幂等新建(ON CONFLICT 的时候表的触发器已经改了桶)
- 一张表只能有一个分桶的数量列;不能是状态机的实体表;逃生口的 SQL 不能直接读这张表

### 4.2 生成的东西(`db/schema/zz_factory_buckets.sql`,`factory prepare`;和当前状态表一样走迁移)

- 桶表 `factory_bucket_<T>`(T 的主键 + `bucket` + Q + 按桶记的列),`CHECK (Q >= 0)`: 不超卖由数据库保证
- 视图 `factory_hot_<T>` = T 的行,Q = T.Q(一直是 0)+ 桶的合计,按桶记的列 = greatest(T 的, 桶里最大的)。
  `INSTEAD OF UPDATE`(差 d = 新 Q − 旧 Q):
  - d < 0(取 −d),**热路径**: 从随机的桶开始,第一个没被锁、又够的桶(`FOR UPDATE SKIP LOCKED`: 不等别人、只锁一个桶),
    在子事务里做 —— 没取到时回滚子事务: 被别人刚改过、重新检查之后不够的行,PostgreSQL 也会留着锁(EvalPlanQual),
    留着去等回退就会和回退互相等(实测死锁,所以这样写)
  - 够的桶都被别人锁着(同时的请求比桶多)→ **排队等随机的那一个桶**(同样在子事务里: 等到之后不够 → 回滚,不留锁)
  - 还是没取到 → **回退**: 锁住 T 的这一行(`FOR NO KEY UPDATE`: 回退的互斥;不挡外键检查的 KEY SHARE),再按桶的顺序锁住
    这个键的全部桶,合计 ≥ −d 才从各桶扣;不够 → 不更新(0 行: 运行时照常判定"条件不成立",和一行的时候一样)。
    热路径的事务只锁一个桶、锁到之后不再等别的;回退一次只有一个 → 没有死锁
  - d > 0(还): 加到随机的一个桶
  - 其他列有变化: 写 T(冷路径)。返回的行 = 之后的合计
- `INSTEAD OF DELETE`: 删 T 的行(T 的触发器删桶)
- T 上的触发器: 新建 / `SET Q`(运维登记、数据修复、旧系统)= **合计设成这个值**(⚖️ H9),平分到 N 个桶,T.Q 置 0;
  负数 → 和 CHECK 一样的错误(23514);改主键 → 桶跟着改;删除 → 删桶;TRUNCATE → 桶也清空
- 编译器: 先按 T 做全部的检查(主键、外键、DRC),最后把 IR 里写 T 的更新 / 删除(`WriteTo`)和读 T 的流水线的表名换成视图;
  生成的 handler 只是表名不同,运行时不变。命令工厂的模型和验收仍按 T(`command.LoadTable` 发现视图时从视图读行)

### 4.3 实测(同一个键,本机 pgbench,`UPDATE … SET q = q - 1 … WHERE q >= 1`)

| 并发 | 一行 | 分桶(16) |
|---|---|---|
| 1 | 1845 tps | 1514 tps(视图 + 触发器的开销) |
| 8 | 1318 tps | 6537 tps(5.0×) |
| 32 | 1412 tps | 10198 tps(7.2×) |

一行的时候并发越多越不涨(行锁排队);分桶之后随并发涨。`make perf`: `runs.consume-job-quota` 8 路都打同一个键(hot:1)= 1 路的 3.5 倍,
锁等待 0%(api-perf 的锁规则照常通过)。

### 4.4 证明

| 什么 | 怎么证 |
|---|---|
| 一行的语义 | 参考实现 = 命令工厂的模型(一行)。状态差分 / 故障注入 / 重放照常(视图上看到的 Q = 模型的 Q);元件认证 `cert_bucket_test.go`(顺序的取 / 还 / 设合计 / 其他列 / 新建 / 删除 / TRUNCATE,每一步和参考比较) |
| 不超卖、不"假的不够" | 验收: `同时抢: 是` 的 API 同一个键 32 个请求同时取 × 3(每个键 16~23 个):成功次数 = 串行执行的成功次数、之后的状态 = 串行执行那么多次的状态;元件认证: 32 个连接同时取 / 还(同一个事务里还写有外键的表),没有死锁、合计 = 参考、桶都 ≥ 0 |
| 变异 | 认证的变异 6 个(热路径不看够不够 / 回退不检查合计 / 还加到全部的桶 / 视图不合计 / 负数不报错 / 删除不删桶);margin 的表结构变异 5 个(每个 ≥ 3 个差分用例) |

## 5. 热键监控(`不确定` / 没回答)

- 生成的 handler: 共享数量的更新的键都是请求的字段时,开头一行 `defer metrics.HotKey("<API>", fmt.Sprint(键…), time.Now())`
  (每项 / 引用前面的操作的键: 不监控)。IR: `API.HotKeys`
- 运行时的指标(`runtime/metrics/hotkey.go`,最近 1000 次写入的滑动窗口;键本身不进标签):
  - `factory_hotkey_window_writes{api}`: 窗口里的写入数
  - `factory_hotkey_top_share{api,top="1"|"3"}`: 最热的 1 / 3 个键占的比例
  - `factory_hotkey_write_seconds{api}`: 一次写入(请求)的用时直方图,等行锁的时间在里面
- 告警规则 `gen/observability/hotkeys.rules.yaml`(`factory prepare` 生成;Prometheus 的规则文件,平台照常抓 /metrics):
  - `FactoryHotKeySkew`: 前 3 个键 ≥ 80% 且窗口写满,持续 10 分钟 → ticket
  - `FactoryHotKeyLockWait`: 写入的 p99 > 0.5s 且一半以上在同一个键上,持续 10 分钟 → ticket
  - 消息就是建议:「<API>: 最热的 3 个键占了 87% 的写入 … 把 同时抢: 不确定 改成 同时抢: 是」
- 平台的接入(把规则文件放进 GitOps 的 PrometheusRule)是平台仓库的事,不在这个 PR(§8)

## 6. perf 和 loadgen

- 单键探针(信息,不失败;⚖️ H6): 按键更新的 API(状态机的转移不算),8 路都打同一个键,报告「同一键的吞吐上限约 N/s」;
  共享数量的读改写另外写建议(会被同时抢 → 同时抢: 是)
- api-perf 的并发检查: 用 API 的键分布(`负载.键分布`;没写 = 平台的默认: `同时抢: 是` → hot:1,其他 uniform)。
  分桶的表 + 热键时,先给每个桶加足够多的量(否则几百个请求就把一个键取光,量的是"不够"而不是热路径)
- loadgen: 不写 `--skew` = 每个 API 声明的分布(同上);写了就用命令行的

## 7. 决定

| # | 问题 | 决定 | 理由 |
|---|---|---|---|
| H1 | 问什么 | 只问共享数量的读改写一个业务问题 | ③ 正是限时抢购的情况;让 ① / ② 也声明只会产生没有意义的 "uniform" 样板 |
| H2 | 不回答 | 按 `不确定`,闸门不失败;AI 审查提出问题 + 建议 | 不能让工厂的门槛变成新人的门槛 |
| H3 | 热点 + 不能分桶的形状 | 静态拒绝,消息里写为什么、怎么改 | 运行时才发现的热点是最贵的 |
| H4 | 分桶放在哪一层 | 数据库(视图 + INSTEAD OF 触发器 + 桶表),编译器把 IR 里的表名换成视图;T 本身不改名 | 生成的 handler / 运行时不变(和并行开发的追踪不冲突);db/schema 里人写的表不动 |
| H9 | 直接写 T 的 Q | = 把合计设成这个值(绝对值) | T 的 Q 一直是 0,`Q + 5` 这种相对的写法在 T 上没有意义;增减走 API(视图) |
| H5 | 桶数 | 16(高级: `负载.桶数`,2~256) | 32 个同时的请求里大多数一次就取到;合计的读取 16 行很便宜 |
| H6 | 单键探针 | 只报告,不失败 | 单键的上限是物理的(行锁),只能告诉人,不能"修好" |
| H7 | 默认的 QPS / p99 | 按 API 种类的平台默认 | 和 slo-platform 的默认 SLO 一致;专家可以改 |
| H8 | factory observe(生产数据 → 建议) | 设计,不在这个 PR | 需要生产的 Prometheus 的接口约定;先有指标和告警 |
