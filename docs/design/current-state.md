# 当前状态表(JSON版本 的"每键最新"物化)

状态: 实现中 · 2026-11-24

## 1. 问题

`存储: JSON版本` 的逻辑表 = 原始表(追加型,每次变更一行)按自然键取最新登记的一行(`pick_per_key`),再去掉删除 / 逻辑删除。
筛选只引用自然键时可以下推到取最新之前(`core/pushdown.go`),用 (键, 登记顺序) 的索引;**非键的筛选**(`category = ?`)
和**非键的关联**(嵌套 `product_master.category = category`)必须先给全部的键取最新,再判断。成本 = 全部版本。
perf 以前把它列为已知边界(`factory/perf/perf.go` 的 versionScan / joinVersionScan),20 万行实测:

| API | 以前 |
|---|---|
| catalog.list-category-shelf-labels | 1.1s |
| catalog.list-product-costs | 0.4s |
| catalog.list-product-master | 0.2s |
| catalog.list-category-products | 0.2s |

`docs/memo/out-of-scope.md` 以前把"最新版本物化表"算作外(写入侧 / 数据管道的事)。这里把它收进工厂: 它能从设计书确定地推出
(原始表、自然键、登记顺序、字段都在 `领域.yaml` 里),也能自证(差分测试 + 元件认证)。

## 2. 做法

每个 JSON版本 的逻辑表 `<view>` 生成一张当前状态表 `factory_current_<view>`(`factory_` 是工厂保留的前缀):

- **列** = 原始表的列(原样复制最新的那一版: JSON、操作列、登记顺序、外壳列)+ 自然键的值 `_k_<键>`(类型 = 字段的类型)。
  一个键一行,包括最新的一版是删除 / 逻辑删除的键(墓碑): 之后再来的旧版本不能"复活"它。
- **唯一约束** `(_k_…) NULLS NOT DISTINCT`(可以为空的键: 空值自己是一组,和 `pick_per_key` 一样)。
- **维护** = 原始表上的触发器(工厂生成,`AFTER INSERT FOR EACH ROW`): 算出这一行的键(和读的流水线同一个式子: 来源单元的
  展开 + 键非空),`INSERT … ON CONFLICT (_k_…) DO UPDATE … WHERE <新的一行的登记顺序更新>`。和写原始表在**同一个事务**里;
  回滚 = 两边都没有。`UPDATE` / `DELETE`(数据修复)= 按键重算;`TRUNCATE` = 一起清空。
- **索引** = 自然键的式子(等值用;文本键另加一份 `COLLATE "C"` 的,给按键的排序 / 分页)+ 读它的 API 声明的筛选 /
  关联的列各一个(式子 = `json_key`,和 SQL 里的条件是同一个生成器: `core.JSONKeyIndexSQL`)。
- **读** = SQL 后端的改写(`core/state.go`,和 pushdown / keyindex 一样只用于生成 SQL): 流水线里
  `scan(原始表) → 展开 → 键非空 → pick_per_key(State)` 换成 `scan(当前状态表) → 展开 → 键非空`,之后的筛选提到展开的后面
  (只越过筛选、只改名的 project、不引用加的列时的 lookup)。**参考求值器仍然跑原来的流水线**(原始表 + 取最新): 差分测试同时验证了触发器和改写。
- **生成物** = `db/schema/zz_factory_current.sql`(`factory prepare` 生成,确定性;和 `zz_factory_platform.sql` 一样走项目的迁移
  流程)。文件是幂等的(`IF NOT EXISTS` / `CREATE OR REPLACE` / 回填 `ON CONFLICT`),对已有的库执行 = 迁移:
  迁移文件 = 这个文件的内容 + Down(`scripts/ci/migrations-check.sh` 的漂移检查保证两边一致)。

## 3. 证明

| 什么 | 怎么证 |
|---|---|
| 状态表 = 每键最新 | 差分测试(参考求值器: 原始表 + `pick_per_key`;SQL: 状态表)× 3 个种子;元件认证 `cert_state_test.go`(随机的登记顺序、删除、逻辑删除、空键、不合法的键) |
| 并发 | 元件认证: 同一个键 16 个连接并发写(登记时刻打乱)→ 状态表 = 对原始表取最新;回滚的写不留下 |
| 回填 | 元件认证: 先有数据、后建触发器 + 回填 = 一直有触发器 |
| 生成器的错 | 认证的变异(`scripts/core-mutate.py`)+ margin 的变异: 写入不更新状态表 / 删除没有反映 / 登记顺序比较反了 / 读的改写丢了键非空 |
| 性能 | `make perf`: 4 个 API < 50ms;versionScan 边界只在没有状态表时适用 |

## 4. 决定(⚖️ 按成熟公司的做法自己定的,PR 里列出)

| # | 问题 | 决定 | 理由 |
|---|---|---|---|
| C1 | 谁维护状态表 | 数据库触发器(工厂生成) | "同一个事务、每一个写"只有数据库能保证: 原始表的写入方往往是工厂以外的系统(旧系统、数据管道),生成的写 API 只是其中之一 |
| C2 | 哪些表有 | 每个 JSON版本 的逻辑表都有(默认);`当前状态表: 否` 可以关掉 | 自动判断"有没有 API 用到非键筛选"会让加一个 API 就改表结构;读最新本来就是这种表的主要用法。关掉 = 回到以前(perf 仍报 versionScan 边界) |
| C3 | 存什么 | 原始表的整行(JSON 原样)+ 类型化的键 | 读的流水线和以前完全一样(同一个展开 / 校验),只是少了取最新;JSON 字段不合法时的行为不变 |
| C4 | 键的值不合法(JSON 里的整数写成 "abc") | 写原始表时报错(触发器里用和读一样的带校验的转换) | 以前这种行会让读这张逻辑表的查询失败;现在在写入时失败(早失败、指到具体的行)。回填遇到 = 迁移失败(要先修数据) |
| C5 | 并发 | `ON CONFLICT DO UPDATE` + 登记顺序比较 | 同一键的写在状态表的行锁上排队,后提交的按登记顺序比较,和提交顺序无关;不同键互不等待。REPEATABLE READ 以上并发冲突 = 序列化错误(重试) |
| C6 | UPDATE / DELETE 原始表 | 按键重算(读原始表) | 追加型表本来不该改;数据修复时也要对。重算在 READ COMMITTED(默认)下正确 |
| C7 | 迁移时的锁 | 建触发器 + 回填在一个事务里(goose 默认) | 期间原始表的写入等待(SHARE ROW EXCLUSIVE);不会漏掉回填和触发器之间的写。大表在低峰执行 |
| C8 | 名字 | `factory_current_<逻辑表>` | `factory_` 是工厂保留前缀;项目的表不能用 |

## 5. 不做(以后)

- 历史读(按日期查某一天的版本)仍读原始表(`按日期` 的关联在原始表的取最新之后): 状态表只存最新。
- 分库: 状态表和原始表在同一个库(触发器是本地的),不跨库。
- 状态表上的部分索引(只索引非墓碑)、按 API 的覆盖索引: 等 perf 说需要再加。
