# 备忘录: 这个工厂不做的(留给以后的其他工厂)

决定(2026-11-17): **这个工厂只做"内"**(见 docs/design/boundaries.md)。下面的需求不往这个工厂里加,
以后如果要做,作为**另外的工厂**设计(各自的基本元件、验证方法、边界)。

| 需求 | 为什么不在这个工厂 | 以后的工厂要先回答的问题 |
|---|---|---|
| 写操作(INSERT / UPDATE / DELETE、事务) | 元件和差分测试都只针对读;写的正确性还涉及并发、幂等、回滚 | 写的"参考实现"是什么?怎么在测试里验证并发和失败恢复? → **另外的工厂已经开始**: 命令工厂(`docs/design/r3-command-factory.md`)。参考实现 = 内存里的模型状态 + 状态差分测试(R3-1);并发 / 失败恢复 = 故障注入(每个第 k 个写操作)+ 并发不变量 + 重放(R3-2,已做) |
| 一个请求访问多个库 / 跨店铺(分片)合并 | 合并的顺序、去重、部分失败的语义不在元件里;一致性在测试里无法复现 | 部分库失败时返回什么?合并后的排序和分页怎么定义? |
| 调用外部服务 / 其他 API | AI 纯函数不能做 IO;外部服务的行为无法用参考实现验证 | 契约测试 / 录制回放?超时和重试的规格写在哪里? |
| 流式 / 异步 / 推送 | 出口只有 one / all / page | 顺序保证、断线重连、背压的规格 |
| 权限 / 行级访问控制 | 平台层的事 | 和认证平台的接口 |
| "最新版本"物化表(追加型表 → 当前状态表的同步) | 是写入侧 / 数据管道的事;工厂只读。没有它,JSON版本上的非键筛选成本 = 全部版本(boundaries.md §7) | 同步的延迟和一致性怎么规定?物化表和追加型表不一致时谁赢? |
| 跨表的复杂报表(多表 join + 聚合 + 排名) | 现在只能走逃生口(手写 SQL),没有差分测试 | join / group by 作为基本元件时,参考实现和认证怎么做 |

试用的数据(一家公司的 101 个参照 API): 外 13 个,全部是跨店铺合并。

## 状态机(R5)不做的(2026-11-23,docs/design/r5-state-machines.md §1 / §8)

状态机只做 saga 需要的最小集合。下面这些不加,真有需求时按核心代数的规矩走"新元件 + 单独评审 + 两个以上的需求":

| 不做 | 为什么 |
|---|---|
| 并行分支和汇合(同时等两个结果) | saga 是串行的;并行要多个状态列 + 汇合的语义 + 部分失败的补偿顺序 |
| 子状态机 / 层次状态、历史状态 | "实体在什么状态"不再是一个列的值,查询(Q7)和指标都变复杂 |
| 人工步骤(HTTP 触发的中间转移) | 另一种入口,先不开 |
| 跨实体的转移(一个转移改两个实体) | 一个转移 = 一个实体的一个事务 |
| 以天 / 周计的计时、日历 | 超时以秒 / 分钟计,由扫描驱动;长计时是调度器的事 |
| 协同式(choreography)的"状态机" | 通知类的订阅用 R4 的消息处理器 |
| 按 subject 有序的消费 | R4 E4: 不承诺顺序,乱序由状态图分类(迟到 → 忽略) |
| 守卫 + 否则 的多分支、一个消息类型从多个状态转移 | 样例里没有需要(实现时缩小,见 R5 设计稿的实现记录) |
