## B1. AI 的部分用本地模型不可用

工厂的设计: 普通的查询(按键取一条 / 多条 / 一览 / 前N条)是**确定性生成**,只有 计算 / 自定义 交给 AI。
确定性的部分这次很可靠(生成 50 秒,验收 3 种子约 3900 个用例 + 变异 53 个全部通过)。问题全在 AI 的部分。

### 现象(实测)

**审查**(factory.yaml `roles.review`,模型 local = winpc 的 qwen3.6:35b,只作参考不阻塞):
- 时间: 每个 API 2–5 分钟(119s / 289s)
- 输出: 两次都不是合法的 JSON(字符串里未转义的引号、结构不完整)→ 工厂解析不了
- 内容: 有错误和幻觉
  - "Go 的 math.Round 是银行家舍入" —— 错。math.Round 是 0.5 远离 0,银行家舍入是 math.RoundToEven
  - "设计稿写的是 list_keyset" —— 幻觉。设计书写的是"多条"
  - "349 和 349.00 是否相等" —— 工厂的验收本来就按数值比较,不是问题
- 和以前的实测一致: 本地模型审查 10 个 API,8 个阻塞问题全是误报(factory.yaml 的注释)

**实现**(`roles.implement`,计算类 GetDailySalesSummary: 十进制的合计、净额、比率、状态):
- 第 1 次: 983 秒写完。正确性未验证(被路径闸门的 bug 挡住,该 bug 已修)
- 第 2 次: 849 秒用完 40 轮,没写完。卡在它自己写的测试的编译错误
  (`big.Int.SetString` / `big.Rat.Float64` 返回两个值,当成一个值用)
- 第 2 次的逻辑代码拿去跑验收: 9 个用例 3 个失败
  —— 十进制格式化丢了小数点("350.75" → "35075")、折扣率总是 0
- **安全网有效**: 错的代码进不了 main(路径闸门 + 编译 + 验收)
- 和以前的实测对比: 本地模型 compute 9 次过 8 次(GetJobSummary,整数 / 浮点)。这次是十进制字符串的精确运算,更难

### 根本的问题

1. 本地模型(35B,量化)对"结构化输出 + 精确的领域规则"不稳定
2. 计算类的设计书这次没有写 `计算例子` → 工厂不生成纯函数的单元测试 → 模型没有快速的反馈,只能自己写测试(而且写错)
3. **不知道计算 / 自定义在真实需求里占多少**。占得少 → 这个瓶颈影响有限;占得多 → 决定性

### 选项

| 选项 | 内容 | 代价 | 风险 |
|---|---|---|---|
| a. 强模型 | 审查和计算类的实现用 claude(factory.yaml 的默认) | API 费用;要 runner 上的凭证 | 低 |
| b. 本地模型 + 约束 | 计算类必须写 `计算例子`;审查改成更简单的输出格式(或 Ollama 的 structured output / JSON schema);解析失败时重试 | 工厂的改动 | 本地模型的上限还在 |
| c. 减少需要 AI 的场景 | 扩充设计语言(新的种类 / 单元: 合计、比率、分类 …),让更多需求能确定性生成 | 设计语言和核心元件的工作 | 要守住"基本元件封闭"(boundaries.md) |

### 第一步(先做,决定方向用)

- 统计试用分支的 75 个 API: 有多少落在 计算 / 自定义 / 手写 SQL 的逃生口;它们各自为什么不能确定性生成
  (缺的是哪个单元 / 种类)。结果决定 a / b / c 的比重
- 计算类 GetDailySalesSummary(已撤回)加上 `计算例子` 再提交一次,看本地模型有了单元测试的反馈后能不能写对

### 完成的标准

- 计算类的 API: 同一个设计书连续 3 次生成都通过验收
- 审查: 输出 100% 能解析;用已知有问题的设计书测,能指出问题(不只是"不误报")

## B2. 设计书本身的错误没有自动的防线

验收 / 差分 / 变异检查的都是"**代码和设计书一致**"。设计书写错了(业务规则错、例子算错、边界没想到),
代码会"正确地"实现这个错误,所有测试都通过。

- 现在的防线: 审查(B1: 本地模型不可用)+ 人
- 这次的设计书是熟悉工厂的人(Claude)写的,没有出错;换成业务的人写,这里就是质量的弱点
- 设计书里的 `例子` 是人算的期望值,算错了会变成"错的标准"(这次 GetDailySalesSummary 的比率是用 Python 核对过的)

### 改善的方向

- 审查要能用(B1)
- 设计书的自检: 例子里能机械验证的部分(合计、比率 …)由工厂交叉检查(例: 业务规则写成可执行的表达式时)
- 设计书模板 / 写法指南,给不熟悉工厂的人(什么必须写进例子: 边界、空值、0 行、上限)
- 影子对比(试用分支的 shadow/)是对"设计书 vs 现有系统"的检查,只适用于有旧实现的 API

## B3. 工厂的缺口只在真实使用时暴露

试用之后**第一个新写的 API**(ListUnclosedSales)就踩到差分数据生成器的缺口:
- 主键 (sales_date, store_code) + 必填的 `store_code 等于`: 生成器让复合键的**最后一列**取唯一值 →
  每个 store_code 只有一行 → 结果永远 ≤1 行 → 覆盖条件"多行"永远不满足 → verify 失败
- 修的时候又发现: 日期 / 十进制的唯一值生成不了(从 3 个值里随机取),320 行被拒绝 311 行
- 已修(6da9b7c): 唯一列避开分组列;日期 / 时刻 / 十进制的唯一值。门槛全过

缺口**不会让错的代码上线**(被挡住),但会让流程停下,要人修工厂。今天还有多少类似的缺口: 未知。

### 改善的方向

- **批量压测**: 准备约 10 份形状各不相同的设计书,真实跑流水线,集中找缺口。形状的轴:
  - 主键: 单列 / 复合(筛选列在前 / 在后)/ 唯一约束
  - 列的类型: 日期 / 时刻 / 十进制 / 可为空 / enum / 邮编(邮编的唯一值也可能有同样的问题,未测)
  - 筛选: 等于 / 属于 / 范围 / 前缀 / 组列表 × 必填 / 可选
  - 固定条件、每组取一条、分页、前N条、分库
- 生成器自己的检查: 生成的数据被拒绝的比例超过阈值(这次 97%)时直接报"生成器的问题",
  而不是表现成"覆盖条件不满足"(今天要读代码才看出来)

### 完成的标准

- 10 份设计书全部一次通过(或者每个失败都变成工厂的修正 + 回归测试)
- 被拒绝的比例 / 覆盖条件不满足时,输出能直接指出原因

## B4. 新表 / 表结构变更没有迁移的路径

- 设计书 PR 只能用已有的表(`design/<领域>/领域.yaml` + `db/schema/*.sql` 由人维护)
- 建表是 `deploy/schema-apply.sh` 的幂等 SQL(CREATE … IF NOT EXISTS),**没有带版本号的迁移**:
  改列、加约束、数据迁移都没有路径
- 真实需求里,新 API 常伴随新表 / 新列
- 和 boundaries.md 的关系: 工厂只读,表的所有者是别的系统。但 dev / 演示环境、以及"工厂自己的表"(jobs 等)需要迁移

### 改善的方向

- 带版本号的迁移(例: 迁移文件 + 已应用的版本表),schema Job 按顺序执行;expand / contract 的规则
- 设计书 PR 里加新表时: 领域.yaml 的表定义 → 迁移文件的生成或检查(和 proto.lock 一样,只追加)
- 先决定: 表结构的权威在哪里(领域.yaml?db/schema?外部系统?)

## B5. prod 的推进没有自动门槛

- api-factory 的 prod = gitops-manifests 的 promote 工作流(PR + 人批准)
- dev 的部署后压测(PostSync k6)失败时: Argo CD 的同步失败 + 告警(ApiFactoryLoadTestFailed),
  但 **promote 的 PR 不会被挡**(GitHub 看不到集群)
- sample-app 的门槛是自动的(压测在金丝雀分析里);api-factory 是 Deployment,没有金丝雀

### 改善的方向

- 集群把 dev 的状态(同步结果、压测结果)写成 gitops-manifests 提交的 commit status(只出不进,不用开放集群);
  promote 工作流检查这个状态
- 或者 api-factory 也改成 Argo Rollouts + 金丝雀分析(和 sample-app 一样)

## B6. 流水线的成熟度和单点

### 第一次真跑修掉的 6 个问题(都已修)

| # | 问题 | 修法 |
|---|---|---|
| 1 | runner 上没有 gh → 结果贴不到 PR | laptop-runner.sh 装 gh |
| 2 | 贴到 PR 的是别的步骤的 $GITHUB_STEP_SUMMARY(每个步骤各自一个)→ 空的评论 | md() 总是写 .factory/ci-summary.md |
| 3 | 路径闸门没有基线 → 确定性生成的文件算成 AI 的改动 | generate.sh 在 AI 之前提交基线(和 loop.sh 一样) |
| 4 | 仓库设置不允许 Actions 开 PR | 打开(can_approve_pull_request_reviews) |
| 5 | 重新生成时推送冲突(机器的分支已经存在) | 强制推送 + 已有的 PR 沿用 |
| 6 | 差分数据生成器的缺口(B3) | 6da9b7c |

一次真跑暴露 6 个 → 第二、三轮还会有,会越来越少。

### 单点

- **笔记本的 runner**: 只有一台。它不在线 → 审查和生成都停(工作流排队)
- **winpc**: 同时跑别的 AI 服务(GPU 抢占);不在线 → AI 的步骤失败
- runner 的用户在 docker 组(= 笔记本的 root)。只因为仓库是私有的、只有一个人能推才可以接受;
  **绝不能**挂到公开仓库

### 改善的方向

- 再跑几轮全流程(B3 的批量压测顺便)
- runner / winpc 不在线时的行为: 超时和明确的失败信息(现在是一直排队)
- 第二台 runner(Mac 也在 tailnet 里)或者 AI 的步骤可以换到强模型(B1-a)

## B7. 速度

实测(2026-11-18,理想路径 = 没有失败的那一次):

| 环节 | 用时 | 备注 |
|---|---|---|
| 设计书 PR: 机械检查 + 试生成 | 8 秒 | |
| 设计书 PR: 审查(winpc) | 每个 API 2–5 分钟 | 结果不可用(B1) |
| 合并 → 生成 + 开 PR | 50 秒 | 确定性;计算类加约 15 分钟(AI) |
| 生成物 PR 的验证(verify) | 5 分 16 秒 | 3 种子验收 + 变异 |
| 合并 → release 完成 | 6 分 42 秒 | 其中 verify 又跑一次 4 分 24 秒、镜像 2 分钟、promote 8 秒 |
| 合并 → 两个集群都在服务 | 7 分 34 秒 | Argo CD 同步 + PostSync(smoke + 压测) |

机器的部分约 15 分钟(不含审查);实际上等人 review 的时间远大于这个。

### 改善的方向

- **verify 去重**: 生成物 PR 上已经对同一棵树验证过 → release 不再跑(按树的 hash 判断);约省 5 分钟
- 审查: 换模型(B1)或改成可选
- verify 本身: 只验收受影响的 API(margin 已经这样做了),全量的放到定时任务

## 小问题

| 问题 | 影响 | 改法 |
|---|---|---|
| PR 说明的"改动的文件"按手动的基准(workflow_dispatch 的 base)列出,包括已经在 main 的改动 | 显示 | pr-body.sh 按生成物的分支和 main 的差比较 |
| runner 上没有内容防护的禁止词清单(~/.config/api-factory/forbidden.txt)→ CI 上 content-guard 跳过 | 公司的词可能进主仓库,CI 查不出来 | 要不要放到 runner 由用户决定(清单本身含公司相关的词) |
| infrastructure-live 的 env.sh 用 BASH_SOURCE 定位 → 在 zsh 里 source 时路径错 | 只影响手动在 zsh 里 source | 改成不依赖 BASH_SOURCE,或说明只给 bash 用 |
| 审查的输出解析失败时只报错,不重试 | 本地模型时几乎每次失败 | 重试 / 让模型修正格式 / structured output |
| 计算类没有 `计算例子` 时不提示 | 模型没有快速反馈(B1) | 设计书检查: 计算类缺 `计算例子` → 警告 |
