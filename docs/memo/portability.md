P6 这次整理掉的泄漏:
- 类型注册表里的 Go 类型 → 挪进 Go 适配器(`goTypes`,按类型的内部 ID)。类型有了和自然语言无关的内部 ID
- `main.go` 直接调用 Go 适配器 → 适配器在 init 里登记,按清单的 `name` 选择(`adapter.Register` / `Manifest.Generate`)
- 适配器的完备性: 注册表里每种出口 / 每种类型,适配器都要有实现 —— `go test` 时失败,不用等到生成代码
- 设计语言能写什么: `docs/design-language.md` 从注册表生成,`make check` 确认是最新的
- 筛选单元的中文名漏进 spec / IR(3 处各自的映射表 + 6 处双重判断)→ 单元库里的内部名,映射只在一处

## 1. 换目标语言(例: Go → TypeScript / Java)

**要写的**
- 新的适配器: IR → 代码。每种出口一个 handler 生成器(现在 5 种)+ 类型映射 + 枚举 + 查询的封装 + 逻辑样例测试(计算)。Go 版 1640 行
- 运行时(platform 的等价物): 服务器、错误转换、分页 token(签名 + 绑定筛选条件)、分库路由、未知枚举的指标。Go 版 660 行
- 清单(manifest.yaml): AI 负责的文件、闸门规则(禁止的 import / SQL 字面量 / 纯函数)、prompt 模板
- 变异的清单(scripts/mutate.sh 改的是生成的 Go 代码)

**不用改的(验证的资产)**
- 验收、自动用例、差分测试、条件敏感度、覆盖驱动的重生成: 全部通过 HTTP(Connect 的 JSON)黑盒地测服务器,**原样复用**
- 核心代数、参考求值器、设计语言、注册表、审查

**怎么确认做对了**: `make accept SEEDS=",s1,s2"` 全过 + 为新语言写同样的变异,`make margin` 每个变异 ≥3。
完备性测试(每种出口 / 类型都有实现)照搬。

**工作量**: 约 2300 行的等价物 + 变异清单。风险集中在运行时的细节(分页 token、分库、错误码),这些都有自动用例。

## 2. 换数据库(例: Postgres → MySQL)

**要改的**
- SQL 后端(core/sql.go,394 行,26 处 Postgres 专用的写法):
  - `DISTINCT ON`(每组取一条)→ 窗口函数 `ROW_NUMBER()`
  - `COLLATE "C"`(按字节)→ `utf8mb4_bin` 之类
  - `::类型` 的转换、`->>`(JSON)、`~`(JSON 字段的格式检查用的正则)→ 方言的写法
  - **列表参数**: 现在是数组参数(`= ANY($1::text[])`、`cardinality`)。MySQL 没有数组 —— 要改成 JSON 参数或展开成 IN,
    **参数的模型变了**(适配器的绑定也跟着变)。这是最大的风险
  - NULL 的排序位置(Postgres: ASC 在后;MySQL: ASC 在前)→ 显式写
- 适配器的查询封装(querygen 317 行): 驱动、类型、数组
- 运行时: 连接池、分库(platform/shard 129 行、server 206 行)
- 验收: 灌数据、读 schema(accept/dbs.go 122 行 + accept.go 的一部分)
- 性能闸门: EXPLAIN 的格式完全不同(perf 595 行,大部分要重写)
- 类型注册表里的 SQL 类型名(每种类型一行)

**不用改的**: 核心代数和参考求值器(语义是数据库无关的)、设计语言、差分测试的逻辑。

**怎么确认做对了**: **元件认证**(core/cert_test.go,692 个用例)对新数据库跑一遍 —— 它逐个基本元件比较 SQL 和参考求值器,
方言的差异会被机械地找出来(这次"JSON 字段的读取 SQL 比参考求值器宽松"就是这样补上的)。然后验收 + margin。

**工作量**: SQL 后端约 400 行重写 + 驱动相关约 600 行 + 性能闸门。列表参数的模型要先设计。
**建议**: 先抽出方言的接口(现在 sql.go 直接写 Postgres),再加第二种方言。

## 3. 换设计语言(例: 中文 → 日语 / 英语)

**要改的**: 设计语言的词分散在各注册表的名字里(没有词汇表层):
- 结构键: TopKeys(15)/ InputKeys(4)/ OutputKeys(5)/ 例子、分页 等子键
- 类型名(9)、出口名(6)+ 各自的键、来源名(1)+ 键(4)、约束的键(4)和值(格式: 数字 / 英数字)、
  关系的写法(3 个正则)、单元名(9,在 cells/standard.yaml;已经有内部名)
- 审查记录的键(问题 / 选项 / 回答 / 补充规则 / 改了设计 / 来自)
- prompt: 审查(约 150 行)、AI 实现(adapters/golang/prompts)
- 报错: 180 条中文

**做法**: 加一层**词汇表**: 内部 ID(已经有: 类型的 ID、出口 / 来源的 Kind、关系的 Name、单元的 id;约束还没有)→ 各语言的写法。
注册表只用内部 ID,解析器和参考文档查词汇表。报错和 prompt 按语言分文件。

**工作量**: 词汇表层的重构(约束和单元加内部 ID、解析器改查词汇表)中等;翻译本身(词 ≈60 个、prompt ≈300 行、报错 180 条)是体力活。
**不用改的**: 核心、IR 以下的全部。spec / IR 里只用内部名(eq / in / valid_at / get_by_id / json_versions …):
P6 之前后加的筛选单元(属于 / 有效期包含 / 不等于)的中文名一路漏进了 spec 和 IR,6 处代码写着"prefix 或 前缀匹配"这样的双重判断;
现在单元库给每个单元一个内部名(`{ id: in, 定义: … }`),映射只在单元库一处。

**怎么确认做对了**: 同一组 API 用两种语言写设计稿,`factory design` 生成的 spec / proto / IR 必须**逐字节相同**(golden 比较)。

## 4. 优先级的判断

| 方向 | 什么时候需要 | 现在做的准备 |
|---|---|---|
| 换目标语言 | 使用者的公司不用 Go | 边界已经干净(适配器登记 + 完备性测试);验证全部可以复用 |
| 换数据库 | 使用者的公司不用 Postgres | 元件认证是现成的方言检查器;方言接口还没有抽出来 |
| 换设计语言 | 给日语 / 英语的设计者用 | 内部 ID 部分就绪;词汇表层没有做 |

都不是现在的瓶颈(P7 的外部验证之前不知道第二个使用者用什么),所以只写到这里,不提前做。
