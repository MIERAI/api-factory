## 审查拦下的真问题(没有审查就会进入实现)

- R4: `LIKE x || '%'` 会把用户输入的 `%` `_` 当成通配符 → 改成 starts_with
- R9: period 不在日本时间 0 点时,日报的语义不确定
- R2: SKU 的空白/大小写怎么处理
- R6: 领域层"金额都是日元"与 schema 的 currency 列矛盾
- R10: proto 注释"超过 N 天"与 SQL/用例的"恰好也算"矛盾(写式样书的人自己的错)
- R2(第 2 轮): review_decisions 说加 CHECK,schema 却没加(操作失误被发现)

## 工厂缺口(按证据排序)

1. **prefix 运算符**(R4): 手写逃生口容易出错(LIKE 通配符),应由工厂生成正确的实现
2. **版本化主数据 as-of**(R6): 领域层已有 `policy: versioned`,有了真实需求
3. **父子资源**(R8 订单头+明细、R5 父资源存在检查): has_many 类模式
4. **派生条件**(R10): 相对时间等,优先级低

## 流程上的发现

- **人工成本的主体不是写 YAML,而是做业务决定**。10 个 API 审查共提出约 13 个需要人决定的问题(平均每个 API 1.3 个)。
  式样书本身平均 38 行,大部分很快写完;真正花时间的是回答"SKU 带空白怎么办""日报跨日怎么算"这类问题。
  → 人的时间应该花在这里,这是审查环节把问题前置的价值,也是测量人工成本时要重点看的部分
- YAML 书写摩擦: 值里带 `: ` 或以引号开头,共 3 次解析失败 → 式样书闸门需要更友好的错误提示
- 一份式样书出错会挡住整批的 prepare(CI 里按 PR 单独验证可避免,批量开发时需要隔离)
- 模式 API(6/10)完全不需要 AI;AI 只用于 compute(4/10),每个约 60~90 秒
