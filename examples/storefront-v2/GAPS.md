# storefront v2 样例项目里发现的工厂缺口

做样例项目时遇到的"工厂做不到 / 做得不好"的地方。每条记：发现时间、形状、当时怎么绕过、要不要修。
(readiness 文档 `docs/design/storefront-v2-readiness.md` 的"探索工具的不足")

| # | 发现 | 形状 | 绕过 | 处理 |
|---|---|---|---|---|
| G1 | R1 catalog | 枚举列是 `SMALLINT`(int16)时生成失败:`query column row.Status (int32) cannot be mapped to enum field status (DB type int16)`。枚举只支持 int32 的列 | 表结构改用 `INTEGER` | 待修:状态类的小整数列很常见(SMALLINT 省空间),类型注册表里整数16 应该能当枚举的数据库类型 |
| G2 | R2-2 order(Q6) | 订单历史的"明细金额合计" = Σ(qty × price)。子聚合的 `合计(列)` 只能对一列求和,不能写表达式 | `order_items.amount` 用数据库的生成列(`GENERATED ALWAYS AS (qty * price) STORED`),合计(amount)。差分测试的造数据不插入生成列 | 暂不修:生成列让"金额 = 数量 × 单价"由数据库保证,比在查询里算更稳。真有第二个需求再考虑聚合里的表达式 |
| G3 | R2-2 order | 嵌套的子行 / 子聚合的列不能是枚举(枚举的映射按来源的表查) | Q5 的明细没有枚举列,没有绕 | 待修:子表的枚举列(例: 明细的状态)出现时再做(子行的消息里映射枚举) |
| G4 | R3-1 catalog(W1) | 表的 CHECK `sku ~ '^[A-Z0-9-]{3,32}$'` 和 `price >= 0`:输入的约束写不出来(格式只有 数字 / 英数字,范围只能用于整数),合法的请求会被数据库拒绝(INVALID_ARGUMENT) | — | 已修(R3-1):格式 `代码`(`^[A-Z0-9-]+$`)、类型 `非负十进制`。写接口的输入必须覆盖表的 CHECK,否则自动边界用例 / 状态差分测试失败 |
| G5 | R3-1 catalog / schedules | 按键更新 的 `写入` 必须是必填:不支持"不传 = 不改"(部分更新);proto3 的布尔即使 `必填: 是` 也分不出"没传"和 false(没传 = false,会被写进去) | 整份覆盖(请求带全部要改的列) | 待定:部分更新需要 optional 字段 + 动态的 SET,差分模型同样处理;布尔的必填要用 optional + required |
| G6 | R3-1 | 命令的输出不能改名(响应字段 = 列名);数据库生成的主键(序号)上的后续操作、外键的表没有差分测试的造数据 | storefront 的 W1–W3 用不到 | 部分已修(R3-2):组合命令的输出用 `来自: 操作名.列` 改名;引用数据库生成的 id(`执行.id`);差分测试按外键的顺序给多张表造数据(子表的外键取父表已有的行)。单个操作的 新建 / 按键更新 仍然不能改名 |
| G7 | R3-2 runs / inventory | 差分测试的模型不知道数据库生成的值(序号、`DEFAULT now()`):模型里是"任意不为空的值",比较时采用数据库的值;新的行按序号的顺序和数据库剩下的行对应 | 引用了不存在的 id(外键违反)、输出取错操作的值(采用之后比较)能抓到;"引用了另一个存在的 id"抓不到 | 待定:模型可以预测序号(RESTART IDENTITY + 每张表的计数器),要处理回滚 / 重试时序号的跳号 |
| G8 | R3-2 inventory(W4) | 表的 CHECK `delta <> 0` 写不进输入的约束(范围只有上下限,没有"不等于") | 设计改成 0 = 盘点没有差异,照样记录(不加这个 CHECK) | 暂不修:真有需要再给约束加 `不等于` |
| G9 | R3-2 payment | 组合命令的输入必须必填;可以不传的输入只能直接写进 新建 / 幂等新建 的值(部分更新 = G5) | RecordCharge 的 reason 只在新建时可以不传 | 和 G5 一起 |
| G10 | R3-2 | 条件只有 比较 + 并且(没有 或者、乘除、函数、`IN`);删除 不能带条件;更新的键引用同一个请求里新建的(数据库生成的)id 时模型按"任意值"找行 | storefront 的 W4 / M1 / M2 用不到 | R4 以后按需要 |
| G11 | R4 inventory(M1) | 表达式里没有时间的加减(`现在 + 24 小时`):预留的过期时间写不出来 | `reservations.expires_at` 用数据库的默认值 `now() + interval '24 hours'`,操作里不写(模型 = 数据库生成的值) | 待定:时间的加减已经在查询工厂里(R2-3 的 `add`),命令的表达式要同一套语义 + 模型 |
| G12 | R4 契约 | 契约的字段不能是枚举(枚举属于一个服务的领域);一个类型同时只能有一个版本(`版本: [1, 2]` 的并行期没做) | 原因 / 状态用 文本(`reason: 'INSUFFICIENT_STOCK'`) | 待定:跨服务的枚举要在契约里声明值;多版本等第一次真正改契约时再做 |
| G13 | R4 | `如果` / 结果的 `当` 在 Go 里判定:只支持 整数 / 十进制 / 文本 / 布尔 / 枚举 的比较(时间不行);`发出` 的值不能写运算(`操作名.列 + 1`) | M10 的规则只比较金额 | 按需要 |
| G14 | R4 | 处理器里 `每项` 的操作的返回值不能写进 结果 的 `发出`(哪一项?);列表只能原样转发(`items: 消息.items`),不能逐项改写 | M1 的 inventory.reserved 原样转发 items | 待定:R5 的 W5(订单 + N 个明细)可能需要"逐项发出" |
| G15 | R4 差分 | 并发的"不同的消息"只用幂等键不重叠的消息(同一个键、值不同的幂等新建: 先提交的赢,没有确定的串行结果);"每项 不排序"的变异(死锁)抓不到:Postgres 检测到死锁 → 事务重试,结果照样对 | — | 记下:排序的效果是"不出现死锁错误 / 重试",要看 `factory_messages_total{outcome="retry"}` 或运行时的重试次数 |
| G16 | R4 模型 | 模型只重现 CHECK 里 `列 比较 整数` 的形状(`held >= 0`),别的 CHECK(正则、长度、IN)靠输入的约束覆盖(G4);消息处理器里写进去的值来自前面的操作(`held - 确认.amount`)时,随机的初始状态可能违反不变量(held < 扣款额)→ 毒消息 | 差分的初始状态里同一个字段写进的几张表取同一批值(`account_id` 对得上) | 记下 |
| G17 | R4 ledger 的审查 | 条件更新的 `不满足: 原因码` 一遇到就回滚(后面的项不再处理),结果的 `当` 在全部做完之后判定:做不到"后面某一项的 当(金额不一致)优先于前面某一项的 不满足(余额不够)" | SettleDebits 用"只读的检查更新"(`设置: { held: held }` + `不满足: 跳过`)把 held 的检查变成 `当`,三个死信原因按结果的顺序判定;DebitAccounts 按账户 id 的顺序先遇到的决定(写进业务规则) | 待定:要么 `不满足` 可以延后(全部做完再判定),要么 `当` 里能写 `操作名.已更新` |
